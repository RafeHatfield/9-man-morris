## Store (gauntlet item 3)

This section is maintained as a **current record**, not an append-log: eight review passes produced eight stacked sections and, five reviews running, the finding was a bullet the code no longer supported. Every bullet below describes the code as it stands. Reversals worth knowing are collected at the end, in one place, instead of left in situ to be mistaken for current design.

### The room and the errors

- **Version is owned by the store, not the caller.** `update(id, fn, expectedVersion)` writes `expectedVersion + 1` and ignores any `version` the callback returns, so there is exactly one place a version can change.
- **Three typed errors, all exported from `@/lib/store`.** `VersionConflictError` (carries `roomId`, `expectedVersion`, `actualVersion`) is the 409 in GDD §7.3; `RoomNotFoundError` is the 404; `CorruptRoomError` is a 500 — a value that should be a room is not one, which is a server fault either way. `update` throws rather than returning a result union: every caller has to handle the conflict, and a `throw` cannot be ignored by accident. **Those three are the only types `update` raises of its own** — every one of them names the room — but two things pass through it unchanged: an exception of `fn`'s own, and anything the injected `RedisClient` throws. `RedisStore.update` awaits `this.get` and `this.client.eval` with no handler, so an Upstash outage, rate limit or timeout arrives as that client's error (`UpstashError` for the real one). That is deliberate: a transport failure is not a statement about the room, and reporting one as `CorruptRoomError` would say it was — which was a claim before it was true: see the CAS-window bullet below.
- **A key holding a non-string Redis type is a known, accepted gap in that contract.** If something `LPUSH`es `room:{id}`, `GET` and the script's `redis.call('get', …)` both raise `WRONGTYPE`, so it reaches the caller as an `UpstashError` rather than the `CorruptRoomError` the contract promises for "something else wrote the key". Closing it would mean wrapping *every* client error, which is exactly what the bullet above refuses — a transport failure is not a statement about the room, and one class of error cannot be wrapped by type without naming `UpstashError` in a store that only knows a three-command interface. Recorded rather than fixed. It is also not reproducible in this suite: `FakeRedis` holds strings by construction. The gap is narrow — every non-room *string* is already answered as `CorruptRoomError`, on both the `get` path and inside the CAS window.
- **`set` is a create/replace primitive, not part of the concurrency protocol.** It writes whatever `version` it is handed and takes part in no compare-and-set, so it cannot be made to reject a concurrent `update`. It is for creating a room, where nothing else can be mid-`update` on that id; everything after creation goes through `update`. Racing them is a misuse with two outcomes, both agreed between the implementations and both pinned: a `set` that keeps the expected version is invisible to the CAS, so the `update` completes and the `set` is lost; a `set` that moves it fails the CAS, so the `update` throws and the `set` survives.

### Concurrency

- **`RedisStore.update` is a Lua compare-and-set (`UPDATE_SCRIPT`), not a read-then-write.** Upstash's REST API has no `WATCH`/`MULTI`, so the version compare and the `SET` have to happen inside Redis or a concurrent writer can land between them and get clobbered. The script returns `[status, version]` so a conflict can report the version that actually won. Four statuses: `1` written, `0` version mismatch, `-1` key missing, `-2` the stored value is not a room.
- **The script has its own "not a room" status, because the CAS window is exactly where that can happen.** `RoomStore.update` promises `CorruptRoomError`, naming the room, when the stored value is not a room; `MemoryStore` delivered that and `RedisStore` did not, in the one window the compare-and-set exists for. `cjson.decode` *raises* on bytes that are not JSON, which reaches the caller as an `UpstashError`; and a value that decodes but has no numeric `version` reached `return {0, room.version}` with `room.version` nil, which in Lua is a *one*-element table, so the caller got `Error: Unexpected result from the room update script: [0]`. Neither carried `roomId`; neither was one of the three types. `pcall` around the decode plus a `type(room) ~= 'table' or type(room.version) ~= 'number'` check turns both into `-2`, which `update` reports as `CorruptRoomError`. The `type(room)` half is not redundant: `cjson` decodes a bare `42` to a Lua number, and indexing one raises — putting the failure straight back on the path the status closes. The memory store's twin of this case stays unreachable: nothing can plant a non-room in a private `Map`.
- **`parseScriptResult` refuses in the same currency.** Anything that is not a pair of numbers is now `CorruptRoomError` naming the room, not an anonymous `Error` — a result the store cannot read means the key holds something this store did not write, which is the same fault by a different route. It renders the offending value through the gate's own `describeValue` rather than `JSON.stringify`, for the reason that helper exists: the `RedisClient` seam is injectable, so the value can be a `BigInt` that `JSON.stringify` throws on. Its `Array.isArray` conjunct is pinned by the one value that clears every other one: `JSON.parse('{"0":1,"1":2,"length":2}')`, an array-like whose `length` is 2 and whose two indices are numbers, which without that conjunct is read as a successful write. The real client cannot produce one — `UPDATE_SCRIPT` returns a Lua array and `update` calls `eval` with no other script — but the seam is injectable, and "not producible today" is the argument this section has thrown out three times.
- **Every script status has a name, and the fall-through is loud.** The constants were `WRITTEN = 1`, `VERSION_MISMATCH = 0`, `NOT_A_ROOM = -2` — `-1` had none, and was handled by a trailing `throw new RoomNotFoundError(id)` that doubled as the fall-through for *every* status the three `if`s missed. So `eval` answering `[7, 7]`, `[-3, -3]` or `[2, 9]` reported `Room ABCD2345 not found` while the room was still sitting under the key, and the client discarded a live game on a 404. `KEY_MISSING = -1` now has its own arm, and anything else is `CorruptRoomError` naming the room and the status — the right currency, because a status this store does not recognise means the script over the key is not the one it wrote. `UPDATE_SCRIPT` as written cannot produce one, which is not a reason to leave it: the `RedisClient` seam is public and injectable, the script is a string that a future edit can change, and "not producible today" has been the wrong argument three times in this directory. All four statuses and the fall-through are pinned by tests through that seam.
- **The pre-read version check is kept, as a fast path — not for the reason it used to give.** It claimed `fn` is the API layer's `apply()` and would throw `IllegalActionError` on a stale position; that is false for every real caller. `handlers.ts` computes the next room *before* the call and passes `() => next`, the join route passes a spread, neither can throw, and `handlers.ts` version-checks before it calls the mutation at all. What the check buys is that a stale caller is refused without an `EVAL` round trip, and that `fn` is never run against a room already known to be stale — which is what makes "`fn` runs at most once, and never on a known-stale room" a property of `update` rather than an accident of its two callers. The read itself cannot go either way: `fn` needs the current room.
- **`MemoryStore.update` has a deliberate write window.** It reads, calls `fn`, `await`s, then re-reads, re-compares and writes. `RedisStore`'s read is a network round trip, so production has that window whether or not the memory store does, and a memory store that is atomic where production is not is exactly where a lost-update bug hides through dev and e2e. The re-check at write time — not the absence of a window — is what makes `update` a compare-and-set.
- **The Redis client is injected into `RedisStore`.** Env handling lives in `get-store.ts`; the store takes a three-command `RedisClient` interface (`get`, `set`, `eval`) that the real `Redis` satisfies structurally, which is what makes the concurrency tests possible without a server. The limit is honest: the tests run the store's real code path against a fake, so they cannot catch a bug in the Lua. The script's full text is pinned by a test as a backstop, so no edit to it can be silent.
- **The client is built with `automaticDeserialization: false`.** The store owns the JSON on both sides of the wire and the script compares what it wrote. Pinned by a test that mocks the constructor, because nothing else in the suite can see it — the store tests inject their own fake client.
- **Auto-pipelining is on, and that is a default nobody chose.** `@upstash/redis` 1.38.4 sets `this.enableAutoPipelining = opts?.enableAutoPipelining ?? true`, and `createStore` passes only `url`, `token` and `automaticDeserialization`, so every command this store issues — the `GET` and the `EVAL` alike — leaves through `/pipeline` rather than the single-command endpoint. The compare-and-set is still correct under it: the auto-pipeline executor returns per-command results and per-command errors in order, and `automaticDeserialization: false` keeps `deserialize` as identity, so a read-then-CAS behaves exactly as it does unpipelined. Harmless, then, and recorded only because nothing in this codebase says it is on and a future reader should not have to rediscover it.

### The value gate

- **One gate, in `types.ts`, used by both implementations on every read and every write.** `roomToJson` / `roomFromJson` / `roomFromStored` are the only ways a room enters or leaves either store, so neither can hold, return or hand back a value the other would not. That includes the pre-parsed object a client built with Upstash's automatic deserialization hands back: it used to be validated and returned *as-is*, so `get` handed out the very object the client held — mutating the result changed the next `get`, an `fn` that mutated and then threw left its damage on it, and a stored `Date` came back a `Date`, which `MemoryStore` could never return. Production never saw it (`createStore` always passes `automaticDeserialization: false`) but the `RedisClient` seam is public and the branch is deliberate, so it goes through the same round trip as everything else. It was invisible for eight passes because the tests compared with `toEqual`, which cannot see identity.
- **`MemoryStore` copies through a JSON round trip, not `structuredClone`,** and holds the JSON string. `structuredClone` preserves `NaN`, `undefined`-valued keys, `Date`s and `Map`s, all of which `JSON.stringify` destroys. Redis stores JSON, so JSON is the semantics that count.
- **Rooms are validated on the way in as well as out.** A room carrying `NaN` used to be *written* and read back as `null` against a field declared `number` — on Redis that bricks the room for its whole 7-day TTL while the memory path keeps serving it: green in dev, dead in production.
- **The gate checks everything checkable without copying the engine.** The §7.4 envelope; `version` and `gameNumber` as whole non-negative counts; and the whole `GameState` — `hand` and `movesSinceRemoval` as counts, `lastMove` as board indices in `[0, POINT_COUNT)`, and the four string unions by membership against the engine's exported `PLAYERS`, `PHASES` and `REASONS`. The engine derives its types *from* those frozen arrays, so importing one is importing the definition, not copying it. **Membership is a strict compare, and that is load-bearing**: `'W' == ['W']` is true, so `isOneOf` written with `==` is not membership at all — an array wearing a player's name would reach `GET /api/game/[id]`'s 200 body as `game.turn`. One row (`turn: ['W']`, refused whole as `game.turn is not a player`) pins it for all four unions, because all four go through the same `isOneOf`. The board's length check is strict in the same way and for a second reason: `Array.isArray` is what makes `board` an array rather than merely something 24 long, and a stored `'W'.repeat(24)` clears every *cell* test, so without that conjunct `get` returns a `Room` whose `game.board` is a **string** typed `Cell[]` — copied into a 200 body, with no `.map` for `legalActions` to call. The row that pins it uses `'W'`s for exactly that reason; with `'.'`s the cell test refused it too and the row passed whether the conjunct was there or not.
- **What the gate does not ask is whether the position is legal** — whether that board is reachable, whether the hand matches the pieces, whether it is really that player's turn. That is `apply()`'s job: a board of 24 White pieces is a well-formed `GameState` and an impossible game, and only one of those is a storage question.
- **`version` is a *safe* integer, not merely an integer.** `Number.isInteger` accepts `2^53`, and `9007199254740992 + 1 === 9007199254740992` — so a room `set` at or above that makes `update` write back the version it read, the compare-and-set never sees a change, and every later `update` pinned to that version wins. Two writers committing from one version is the single thing this store exists to prevent, and only this gate stands between `set` — public API — and that hole. `Number.isSafeInteger` closes it, and a room at `MAX_SAFE_INTEGER` now fails its next `update` loudly rather than degrading into a silent no-op.
- **`id` and `version` are store-owned, and one policy covers both — refuse, never correct — but they are not symmetric.** `id` is checked against the **key**, on the pre-image and again on the post-image: two sides, one question. `version` has no store expectation to disagree with on the pre-image — `set` accepts whatever version it is handed and `update` supplies its own — so its only cross-check is post-image against the value that went in: one side, asking whether serialising changed it. `update` is not stricter for it, because `update` does not *correct* those fields, it *supplies* them — it passes `{ ...fn(room), id, version }` and the check then agrees. The distinction is between a caller that derives a room (store writes the two fields) and one that hands over a whole room (store verifies them). That pre-image `version` is read *inside* the read guard, next to the validation, not repeated after serialising — a getter may throw on its second read as easily as its first — and is pinned by one that answers once and then throws. The `id` compare carries one more job than the disagreement it is named for: `whyNotARoom` checks every declared §7.4 field **except** `id`, so `room.id !== id` is the only thing that types `Room.id` as a string at all. It is therefore strict for two reasons, and pinned by an id that a loose compare would accept — `['ABCD2345']` coerces to the key, and is refused as `room announces id ["ABCD2345"]`. The `id: 12345` fixture that used to stand here could not see the difference: `==` refuses a number as readily as `===` does.
- **The post-image is checked because `toJSON` decides what is actually emitted.** The object that was validated and the bytes that get written are not the same thing: a room serialising to `{ ...room, version: 1 }` let three successive `update(id, fn, 1)` calls all succeed, each clobbering the last. A room can also fail to become JSON at all, and every way it can is reported as `CorruptRoomError` rather than as whatever JavaScript threw — because a `SyntaxError` or a `TypeError` from inside the gate is indistinguishable, in an operator's log, from a bug in the store itself. `JSON.stringify` *returns* the value `undefined` for a `toJSON` yielding undefined, a function or a symbol (which then parses to a `SyntaxError`) and *throws* on a cycle or a `BigInt`. The error-message builder is wrapped for the same reason: `JSON.stringify` throws on a `BigInt`, so the gate could not report the one thing it had been asked to report.
- **The stored bytes are the ones that were validated, never a second pass over the caller's object.** Serialising the caller's object twice would call its `toJSON` twice, and one that answers differently each time would have one value validated and a different one written. That is a property of *which* string is returned, not of serialising again: `JSON.stringify(JSON.parse(json))` is the identity on anything `JSON.stringify` produced, so the second serialisation was dead work and is gone.
- **`timerMs: null` is GDD §5.3's *None* option, and both stores round-trip it.** Every other room in the store suite is built with a 5-minute timer, so the null arm of the `timerMs` guard was executed by nothing here and dropping it survived the whole suite — a store that 500s on every timerless room, on the write and on the read, would have looked identical from inside this item. (It was killed only by `endpoints.test.ts`, in another item's suite, which is not a pin this item can claim.) One row on both implementations — `set` a room with `timerMs: null`, `get` it back null — now holds it.
- **Stored rooms are not Zod-validated** — the structural check above does the work. Zod is for untrusted request bodies at the API boundary (GDD §8.6), and a full room schema would duplicate `GameState`.

### Choosing a store

- **REST credentials are read as pairs, and blank means absent.** Reading "first url found, first token found" with `??` mixed one integration's url with the other's token, and let a declared-but-blank `KV_REST_API_URL` beat a working `UPSTASH_REDIS_REST_URL`. Values are trimmed; `''` and `'   '` count as absent — Vercel keeps a variable declared with no value, and untrimmed whitespace survived every guard and then failed inside `new Redis()` as "invalid URL", naming nothing to fix.
- **Store selection keys off the REST pair, never `REDIS_URL`.** `@upstash/redis` speaks REST only and cannot use a TCP url.
- **On a deployed runtime, nothing configured is exactly as fatal as half configured.** Treating "the Marketplace integration was never added" as normal while a half-set pair was fatal made the likelier misconfiguration the silent one. **Off a deploy the two deliberately differ, in volume and only in volume:** both fall back to `MemoryStore`, but a half pair warns and nothing at all is silent — no Redis variables on a laptop is the ordinary local case and has nothing to report, while a half pair is someone's half-finished attempt at configuring one. The deploy decides the severity; the evidence of intent decides the warning. (This bullet used to say the two get the same signal *everywhere*, and then said in its own last sentence that zero variables warns nothing.)
- **A deployed runtime is `VERCEL=1` with a `VERCEL_ENV` that is not `development`** — `development` being `vercel dev`, a laptop, and the only carve-out there is. Every other value counts, **absent and blank included**. Requiring `VERCEL_ENV` to be *present* was never argued for and put the silent memory-store fallback one absent system variable away from production: `VERCEL=1` with no `VERCEL_ENV` and no credentials returned `MemoryStore` with no throw and no warning at all. Of the two ways to be wrong about an environment this cannot classify, refusing to start a deploy costs a minute and serving a store that loses every room between invocations does not announce itself — so absent, blank and unrecognised all fail closed. There is deliberately **no build carve-out** either: excluding `NEXT_PHASE=phase-production-build` put one more environment variable ahead of the guard, on the silent path. It was also unnecessary — every route is `force-dynamic` and `getStore()` is only called from a request handler, verified by building with no credentials under both `VERCEL=1 VERCEL_ENV=production` and a bare `VERCEL=1`, which succeed.
- **`isDeployedRuntime` is not exported.** The API layer scopes its own `MORRIS_E2E` timer escape by a different question — a client request never arrives during a build, so "not running on Vercel at all" is the honest condition there. Two predicates asking different things are two definitions, not one duplicated; sharing this would have made the next change to either a change to both.
- **A test run takes the memory store; a test lever on a deployed runtime is refused rather than resolved.** `VITEST` (any non-blank value — it is read through the same trimming `read()` as every other variable, so a declared-but-blank `VITEST` is not a lever; the runner sets it in every worker) or `MORRIS_E2E === '1'` (meant to be set by hand, so exactly `'1'`) selects `MemoryStore` even against a complete valid pair, because a developer who has run `vercel env pull` would otherwise have `npm test` and Playwright's `webServer` writing to production Redis, against §8.3. But when a lever is set *and* the environment looks like a deploy, both silent answers have a demonstrated failure mode — honouring it hands production a store that loses every room between invocations; ignoring it points a test run at production Redis — and the environment cannot tell the two apart, because `vercel env pull --environment=production` with system variables exposed puts `VERCEL=1` and `VERCEL_ENV=production` on a laptop. So that combination throws, naming both ways out. Refusing to guess is the only answer that is not silently wrong in one of the two worlds.
- **Room ids are 8 characters of Crockford base32 minus `0` and `1`** (`23456789ABCDEFGHJKMNPQRSTVWXYZ`), uppercase so a shared link is not case-sensitive, from `crypto.getRandomValues` with rejection sampling so every symbol is equally likely. **Player tokens are 16 bytes as 32 hex characters.** They differ because they are different kinds of secret: an id is a *name*, read off a screen and typed by hand, and knowing one grants only a spectator view; a token is a *bearer credential* nobody ever types. So the id is sized for humans (30^8 ≈ 6.6e11 over a 7-day TTL) and the token against guessing (2^128). The `30^8` is pinned per byte *position* — a draw of zeroes with a single `1` in it must move exactly the character that byte feeds and nothing else — because every test that fills a draw uniformly is blind to which byte is read, and a generator reading one byte per draw yields ~2,600 distinct ids. The sampled distinctness check is kept alongside it with a one-collision tolerance: zero tolerance over 30^8 fails a legitimate run 1 time in 3,300, two collisions is ~5e-8. **The alphabet string itself is pinned character for character**, for the reason `UPDATE_SCRIPT` is: no edit to it may be silent. Every other property asserted about it is an *absence* — five characters it must not contain, distinctness, uppercase-invariance — and `'2345678/ABCDEFGHJKMNPQRSTVWXYZ'` satisfies all of them while putting a `/` in a room id, which breaks the share link because `/g/AB/D2345` does not route.
- **No TTL in `MemoryStore`.** GDD §7.2 asks for the 7-day TTL on the Redis keys; the memory store lives and dies with the process.

### Standing rules for this item

- **The error path can throw as easily as the happy path.** `throw null`, `throw undefined` and `throw 'a string'` are all legal, so `(cause as Error).message` inside a `catch` threw a `TypeError` out of the very handler written to stop `TypeError`s escaping — and a string cause rendered as `undefined`, the exact defect fixed for `describeValue` two functions earlier. Causes are read through one helper, `tried`, which cannot throw, and rendered by another, `describeValue`, which names what actually arrived. `tried` sits at **module scope**, not inside `reason`: it was a local of `reason` for four passes while `guardingReads`, two functions below, wrote `cause instanceof CorruptRoomError` directly — and `instanceof` invokes `[[GetPrototypeOf]]`, which a `Proxy` can trap and throw from, so the guard written to stop raw exceptions escaping threw one itself. A `Proxy` with a throwing `getPrototypeOf` trap came out of `set` and `update` as a bare `Error: boom` on both implementations — eight paths, none of them one of the three types `RoomStore.update` promises and none naming the room. That is fixed, and pinned: the `it.each` over hostile causes now carries a row whose thrown value is exactly that proxy, and it is the only row that can see the difference, because every other row has a readable prototype. The same row also pins `reason`'s own `tried(() => cause instanceof Error)`, which a bare `instanceof` had been passing for four passes. The helper names what arrived — including the `Error` whose `name` is not a string, since `name` is as writable as `message` and the fallback is what stops "an unreadable Error" degrading into "an unreadable 42" or "an unreadable undefined". `describeValue` is exported for the one caller outside the gate, `RedisStore`'s script-result parser, which has the same problem with the same values.
- **Reading a room can throw, and that is the gate's problem too.** Validation *reads* every declared field, so a getter on `version` or `game`, or a `Proxy` that throws on any read, escaped verbatim — while a throwing getter on an *undeclared* field was reported properly, because only `JSON.stringify` ever reached that one. Every read of a caller's object is guarded, including the spread `update` uses to apply the store-owned fields — and, since this pass, including the two places where the *error path itself* read one directly and neither `tried` nor `describeValue` was reached. **`assertRoom`'s id-disagreement message** built its text with `JSON.stringify(room.id)`, the exact defect `describeValue` exists for: a bigint id made the message builder throw, so a room refused for disagreeing with its key was reported as `the room could not be read (Do not know how to serialize a BigInt)` — a serialisation complaint for an id disagreement — and a symbol id rendered as `room announces id undefined`, saying nothing about what arrived. **`roomToJson`'s CAS-defeat message** interpolated `given` bare, and `given` is the *second* read of a caller's `version` getter: a getter answering a valid count for the validator, a symbol for `given`, and a valid count again for `JSON.stringify` produced a well-formed post-image, reached the version comparison, and threw `TypeError: Cannot convert a Symbol value to a string` from **outside** `guardingReads`. Both now go through `describeValue`, and both have a test that fails without it. The rule these three share is the one to carry forward: **a value read off a caller's object is caller-controlled at every later use, including inside the handler that reports it** — the type on the field is not a guarantee, because a getter supplies it. The one read deliberately left unguarded is the call to `fn` itself: a caller's exception is the caller's and must arrive unchanged, which is pinned by identity rather than by message, because `toThrow('boom')` is a substring match that a wrapper quoting the cause would satisfy.

### Reversals worth knowing

Kept short, so a reader knows what not to re-propose:

- **Do not silently normalise `id` on the way in.** It was `{ ...room, id }` for five passes, which is the opposite policy to the refusal on the way out — the same field, a few lines apart.
- **Do not delete the post-serialisation check.** It was deleted once as unreachable; `toJSON` reaches it, and the result was an accepted write that then 500s for the room's whole TTL.
- **Do not scope the loud failure by `NODE_ENV`.** `next start` — which the e2e webServer runs — is `NODE_ENV=production`, so that would leave the suite exposed to the very failure the scoping exists to prevent.
- **Do not check the engine's string unions with a local copy of their values.** That is a mirror; import the engine's exported lists, which its own types are derived from.
- **Do not treat a `MemoryStore` fallback on a deploy as acceptable because it is convenient for tests.** It looks like a working deploy from outside and loses every room between invocations.
- **Do not classify a mutant as equivalent by argument.** Build the input that would distinguish it. The one time that was done by reasoning here, the reasoning was wrong and a live guard was recorded as dead code.
- **Do not use `Number.isInteger` for anything the store does arithmetic on.** Above `2^53`, `+ 1` is a no-op and the compare-and-set silently stops working.
- **Do not make the deploy guard require `VERCEL_ENV` to be present.** A missing or blank system variable is not evidence of a laptop, and that reading put the *silent* memory-store fallback one absent variable away from a production deploy. Only `development` is a laptop.
- **Do not let `RedisStore` answer a corrupt room with anything but `CorruptRoomError`.** A plain `Error` from the script-result parser, or an `UpstashError` out of `cjson.decode`, breaks the contract on `update` and reaches the API layer as an unclassified 500 that does not name the room.
- **Do not report an unrecognised script status as a room that is gone.** `RoomNotFoundError` is a specific claim, and the client acts on it by discarding a live game. An unrecognised status is a statement about the script, not about the key.
- **Do not read a caller-controlled value with a bare `${…}`, `JSON.stringify`, `String(…)` or `instanceof` — the error path included.** `tried` and `describeValue` exist for exactly that, and this has now been the finding in four separate places, twice inside the handler written to prevent it. The type declared on a field is not a guarantee when a getter supplies the value.
## Board UI (gauntlet item 5)

- **Point coordinates live on a 6×6 integer lattice, not in pixels.** `src/components/geometry.ts` stores each point as `{gx, gy}` in 0–6 and projects it into a `0 0 100 100` viewBox with `PADDING + g × STEP`. The lattice is what `geometry.test.ts` reasons about (collinearity, even spacing, "no point between"), so the topology check is exact integer arithmetic rather than float comparison. Pixel size is then one number, set by CSS.
- **The 16 board lines are the engine's 16 mill lines.** `SEGMENTS` is `MILLS.map(...)`, drawn first-point to last-point. There is no second hand-written list of lines that could drift from the rules, which is the §7 "single source of truth" rule applied to the picture.
- **The adjacency test runs both ways, using the drawn lines to define "neighbouring".** Two points are neighbours in the picture when one drawn mill segment covers both and no third point lies between them. That definition is what makes the empty centre correct: 17–21 and 23–19 share a column/row but no drawn line spans the gap, so they are not neighbours — matching `ADJACENCY`. The test asserts the engine's 32 edges and the picture's 32 edges are the same set, so a wrong table on either side fails.
- **Hit targets are HTML `<button>`s laid over the SVG, not SVG elements.** GDD §6.5 asks for real buttons with `aria-label`s; SVG has no button element and `foreignObject` is worse. The SVG is `aria-hidden` and decorative, and 24 absolutely-positioned transparent buttons carry the semantics and the taps. Each is `STEP` (14 viewBox units) square = 45.92 px at a 360 px viewport — the arithmetic is in `geometry.ts` and asserted in `geometry.test.ts`.
- **Tap size equals the lattice step**, which is also the closest distance between two points (the inner ring). That is the largest target that cannot overlap its neighbour, and it clears 44 px with room to spare — so when a target is too small the fix has to be its shape, not its size.
- **`geometry.ts` holds the layout numbers the DOM actually uses, not a model of them.** `BOARD_MARGIN_PX` (16), `BOARD_MAX_PX` (520) and `PAGE_MAX_PX` (640) were at first only read by the test, while the render got the same numbers from `p-4` and `max-w-[520px]`. That is the "never mirror" rule broken in the one place it matters: swapping `p-4` for `p-8` dropped the real target to 41.4 px with the suite still green. The pages now render `style={{ maxWidth: PAGE_MAX_PX, padding: BOARD_MARGIN_PX }}` and `Board.tsx` renders `style={{ maxWidth: BOARD_MAX_PX }}`, so `boardWidthPx()` composes the same three values the browser lays out with and the §6.2 assertion moves when the layout does. Verified by setting `BOARD_MARGIN_PX = 32`: the test went red *and* the rendered target measured 41.44 px.
- **The tap button must not be rounded, and `geometry.ts` owns that fact.** The first version used `rounded-full`, which browsers hit-test as a circle: the box stayed 45.92 px but the largest square a thumb could actually land in was 45.92 / √2 = 32.47 px, and real clicks 20 px diagonally from the centre fell through to the SVG plate. §6.2 permits "invisible larger tap circles", but the 44 px claim in this file and in the test was then false as rendered. `TAP_SHAPE_CLASS` and `tapHitSquarePx()` now express the shape and the usable area together, `Board.tsx` applies the class, and the test asserts both the 44 px floor and the shape that makes it true.
- **`Board` decides it is inert from its inputs, with no extra prop.** No `onPointTap`, or an empty `legal` list, means every button is `disabled`. - **What a tap *means* is a pure function, `interpretTap` in `src/components/interaction.ts`.** It only looks the point up in the `legalActions()` list, so it holds no rules, and both `/local` and the online page share one copy of the select / deselect / move / remove logic. The only thing the component adds is *whose* piece landed there, which is a fact about the board rather than a rule; the point a move lands on was empty beforehand, so every mill through it is newly formed.
- **The pure parts of the components live in `.ts` modules, so they can be tested.** `boardModel.ts` (per-point marks, the flashing mill, inertness, the `aria-label` wording) and `chromeModel.ts` (headline, detail line, piece counts) hold every derivation; `Board.tsx`, `StatusBar.tsx` and `BottomBar.tsx` are JSX over them and nothing else. Testing the components themselves would need jsdom or testing-library, which GDD §8.6 does not allow, and the alternative — leaving §6.2–6.4 unverified until item 7's e2e — is worse. The read-only board of §6.4 is exercised this way today, before any page passes an empty legal list.
- **`overflow-x: hidden` removed from `body`.** It came from the scaffold. It clips horizontal overflow instead of preventing it, which would have made GDD §8.4's no-horizontal-scroll assertion unfailable; with the rule off, nothing overflows at 360 px anyway, so it was buying nothing and hiding the next regression.
- **`/local` gets a placeholder "New game" button.** Gauntlet item 6 owns rematch and the finished-game banner; without some way to restart, the page is unplayable after the first result and cannot be screenshotted for the mobile pass. It is two lines and item 6 should replace it.
- **Hot-seat applies actions as `state.turn`.** In §5.2 the player to move is whoever is holding the device, so there is no seat to check.

## Engine (gauntlet item 2)

- **A decisive result beats the 50-move draw.** GDD §4.6 gives no precedence for a move that both completes the fiftieth movement-phase move and leaves the opponent with no legal move. `endTurn` now passes the turn, runs the §4.6 loss checks, and only declares `draw50` if the game is still alive — so that move is scored `blocked`, a win. Rationale: the draw exists to end games that are going nowhere; a game that just ended decisively is not one of those, and the chess analogy (mate on the fiftieth move is mate) is the settled one. Pinned by a test in `rules.test.ts` (C16).
- **"50 consecutive moves" is 50 plies, not 50 per player.** GDD §4.6 says "50 consecutive moves in the movement phase with no removal" and §7.1 names the counter `movesSinceRemoval`; §4.4 calls one slide a move. Read literally, that is 50 slides in total, and the engine counts it that way. The conventional Nine Men's Morris rule is 50 per player, which would draw half as often — noted because it is a real gameplay difference (in 2000 random playouts the literal reading drew 47% of games, though random play forms far fewer mills than real play). The GDD wins; changing it is a one-constant edit to `DRAW_MOVE_LIMIT` — which is itself pinned at 50 by a test that plays forty-nine plies without a draw and draws on the fiftieth, so the constant cannot be edited quietly.
- **`legalActions` lists board actions only.** `resign` and `forfeit` are deliberately excluded: either player may resign at any time whoever is to move, and a forfeit is issued by the server against the player on the clock. Both are validated in `apply`. This keeps `legalActions` exactly what the board UI needs to drive a tap.
- **A mill with nothing to take passes the turn.** If a placement or move forms a mill while the opponent has no pieces on the board, `pendingRemoval` is not set — otherwise the turn would deadlock waiting for a removal that cannot happen. Unreachable in legal play — during placement the opponent always has at least two pieces on the board when the mover moves, since removals can never outrun placements, and in the movement phase they would already have lost — but the branch is defined rather than left to chance.
- **`formsMill` validates its point.** It is public §7.1 surface, so an off-board index throws `IllegalActionError` like every other entry point here rather than a raw `TypeError` from an undefined table lookup — one error type across the whole surface, whoever calls it. (Nothing outside the engine imports it today; the UI's mill query is `millsThrough`.)
- **A fourth critic's constructed-position oracles were declined.** They check the §4.6 end-of-turn verdict and the §4.5 protection rule against oracles written from the GDD over tens of thousands of *constructed* positions, reaching a density of blocked and mill-out endings that random self-play does not (the shipped fuzz reaches `blocked` in roughly 9 games in 2000). The judgement is that the ground is already held from three other directions — the §4.6 clause boundaries are pinned by hand-built fixtures in `engine.test.ts`, protection and the all-in-mills exception line by line in `rules.test.ts` and `reference.test.ts`, and the whole state machine field-by-field against an independent reference — and that a fourth oracle buys less than its runtime costs on every `npm test`. Recorded because it is a real trade rather than an oversight: if a rules defect ever escapes this suite, constructed-position oracles are the first thing to add.
- **Three critics' adversarial suites were kept**, because each reaches something the hand-written tests do not. `rules.test.ts`: a `legalActions`↔`apply` property test and a seeded self-play fuzz over 200 games asserting structural and rules invariants. `adversarial.test.ts`: an independent re-derivation of the board tables from the §4.1 picture, a 10,000-position cross-check of `formsMill`/`removablePieces` against a reference, and freezing cases aimed from a different direction than `engine.test.ts`'s own immutability block. `reference.test.ts`: a second reference engine transcribed from GDD §4 with its own tables, compared against every state of hundreds of seeded games on every field but `lastMove`, which its own case covers separately, plus proofs that colour swap and a two-index ring rotation are symmetries the engine commutes with. Those two are about the engine, not the tables: a corrupted table that happens to stay symmetric passes them, and it is `board.test.ts` and the two independent hand-derivations that catch that.
- **An agreed draw is a function, not an `Action`.** GDD §4.6 requires agreed draws but §7.1's `Action` union has no member for one, and §7.1 is the contract this item is built to. So the engine exposes `agreeDraw(state)` — pure, and still the only place `result` is set — rather than inventing a sixth action. The offer and the acceptance are not engine business: they are two booleans on the `Room` (§7.4 `drawOffer`), and `POST /api/game/[id]/draw` (§7.3) calls `agreeDraw` only once both are set. That keeps GDD §7.3's "all mutation goes through `apply()`" honest in substance — no route ever edits a `GameState` by hand — while leaving the §7.1 signatures untouched.
- **`millsThrough` was added for the board UI.** GDD §6.3 asks for the pieces of a formed mill to flash, and §4.5 allows one move to form two mills, so the UI needs the actual lines — not a boolean. Putting the query in the engine keeps "which line is a mill" out of the components (`CLAUDE.md`), and `formsMill` (§7.1) is now defined in terms of it, so there is one implementation rather than two.
- **Every state the engine hands out is deep-frozen.** GDD §7.1 opens "Pure functions over an immutable `GameState`", and the board tables are frozen for the same reason — but `{...s}` is a shallow copy, so a returned state used to share its `hand`, `lastMove` and `result` with the state it came from, and on some paths not others. One `seal()` at the three public exits (`initialState`, `apply`, `agreeDraw`) rebuilds and freezes every sub-object, so "immutable" is enforced rather than promised and no returned state can be written through into one the caller does not own. `seal` copies before freezing, so the input is never frozen as a side effect.
- **`apply` refuses three state shapes outright, but only for board actions.** `unplayable(s)` names three shapes that would each corrupt the rules rather than merely end the game — none of them reachable from `initialState()`, which is the closure that matters, though a state handed in from outside can be played into one (a placing position with unequal hands strands the shorter-handed player): a board that is not 24 points, a pending removal against an opponent with nothing to take, and a placing mover with no removal owed whose hand is not a positive whole number. It is deliberately not a general soundness check — a state can be stuck for reasons it does not name (a walled-in mover in the movement phase, a full board with pieces still in hand), and those are left alone, because `legalActions` already returns `[]` for them, the three exits still work, and nothing is miscounted. `place`, `move` and `remove` throw for all three, and `legalActions` returns `[]` for them, so the board never offers a hint the server would refuse. **Resignation, forfeit and an agreed draw are deliberately not guarded**: they are how a game ends, and a stuck room is precisely the room that needs its exits — guarding them would turn a room with three ways out into a room with none. The shapes only arrive from outside the engine (a store, a hand-built fixture); nothing about whether the *position* is reachable is checked, because that is `apply`'s business one action at a time.
- **The 50-move draw is gated on the movement phase**, matching GDD §4.6's wording rather than relying on the counter only rising there — a state from a store need not agree.
- **The barrel is a list of what the app imports.** `index.ts` names its exports explicitly rather than re-exporting `*`, so the public surface of `@/lib/engine` is exactly what something outside the engine consumes: §7.1's five functions and its types, plus `MILLS` (the board's geometry derives its drawn segments from it), `ADJACENCY` (what the geometry test asserts the drawn neighbours against), `POINT_COUNT` (the store validates a stored board's length), `Reason` (the result banner's text table), `PLAYERS`/`PHASES`/`REASONS` (the store checks membership without restating the literals), `IllegalActionError` (the API tells an illegal move from a server fault), and `opponentOf`, `millsThrough` and `agreeDraw`, each with its own entry here. `POINTS`, `LINES_THROUGH` and `DRAW_MOVE_LIMIT` stay exported from their own modules, which is how the engine's own tests reach them, and are **not** on the barrel because nothing outside imports them. `PIECES_PER_PLAYER` and `isOver` are not exported from anywhere: their only callers are in the files that define them. `Result` is off the barrel too — nothing outside names it, and `GameState.result` carries the shape structurally. A test pins the absence of those five names by reading `Object.keys` of the barrel — three of them are values exported elsewhere, two are exported nowhere, and either way the barrel must not carry them — and a `@ts-expect-error` import pins `Result` separately, since `Object.keys` cannot see a type-only export and an entry there would be an assertion that cannot fail — so any of them reappearing on the public surface is a failure rather than a drift.
- **The three closed alphabets are exported as runtime lists, and the types are derived from them.** `PLAYERS`, `PHASES` and `REASONS` are frozen `as const` arrays in `types.ts`, with `Player`, `Phase` and `Reason` defined as `(typeof X)[number]` — so each alphabet has one definition rather than a list and a union that can drift apart. GDD §7.1 writes them as unions; deriving the union from the list produces exactly that type. The reason they exist at all is the store: it validates a room read back from Redis, `GET /api/game/[id]` copies `game` into a 200 body without `apply()` ever seeing it, and without a runtime list the store's only options were to restate the literals (which `CLAUDE.md` forbids) or to let `phase: 'flying'` through to a client.
- **`opponentOf` is exported; `isOver` is internal.** `opponentOf` is used by the UI chrome. `isOver` — the single definition of "finished", counting a state as over if *either* `result` or `phase` says so, so a state that arrives half-set from a store cannot be live for `legalActions` and over for `apply` — stays internal: every consumer that needs the question answered already reads `result !== null`, which is equivalent for any state the engine produced, and an export nothing imports is one more piece of surface to keep honest.

## API (gauntlet item 4)

- **One shared write path, `mutateRoom`.** Every endpoint that changes a *game* — `/action`, `/draw`, `/rematch`, `/claim-timeout` — loads the room, resolves the caller's token to a seat, computes the next room and writes it through `store.update`. `/join` is the exception and cannot use it: the joiner has no token to resolve, so it runs its own read-check-write loop with the same shape, sharing `MAX_WRITE_ATTEMPTS`, the refusal wordings and the `guarded` safety net, but mapping its own store errors. The next room is computed *outside* the update callback and the callback returns it verbatim; that is safe because the store re-checks the version at write time (in Redis, inside the Lua script), so a writer that lands in between causes a conflict rather than a clobber. The alternative — doing the work inside the callback — would put engine calls inside a Lua-guarded critical section for no gain.
- **Refusals are thrown, not returned.** `ApiFailure(status, message)` is thrown from inside a mutation and turned into a response by `mutateRoom`; `IllegalActionError` from the engine becomes a 400, `VersionConflictError` a 409, `RoomNotFoundError` a 404. That mapping lives in `mutateRoom`, and `/join` — which does not go through it — repeats the two store errors it can see, because its conflict means something the shared path cannot know: that the seat may have just been taken. Anything neither of them recognises becomes the 500 described below.
- **`expectedVersion` is mandatory on `/action` and absent everywhere else.** The action endpoint is the only one where the client is acting on a board it has drawn, so it is the only one that can be stale. Claim-timeout, rematch and draw carry no version: they use the version just read and, on a conflict, recompute from the fresh room, three attempts in all. Two players tapping Rematch in the same instant both get a 200 — tested — rather than one of them getting a 409 it cannot act on.
- **A `forfeit` action is refused (403) at `/action`, but only once the room's state has been judged.** It is structurally one of the engine's five actions, so Zod accepts it, but the engine would happily award it to whoever asks as long as the victim is the player on the clock; only `/claim-timeout` may issue one, after checking the elapsed time against the server's clock. The refusal sits after `requireBothSeats` and the finished-game check — so a forfeit sent to a finished game is the same 409 as every other action, not a 403 — and before the turn check, so the reason given is the real one whichever seat sent it.
- **Wrong turn is a 403 and an illegal move is a 400 — once the version has been accepted.** The engine throws `IllegalActionError` for both, so the turn is checked in the route before `apply` and mapped to 403 per GDD §7.3. Both are judged only after the `expectedVersion` pre-check below: an action that is stale *and* out of turn is a 409, because the client's board is what is wrong. `resign` is exempt from the turn check: either player may resign at any time, on either player's clock.
- **Within a game, `turnStartedAt` moves only when the turn changes seats.** After `apply`, `/action` compares `game.turn` before and after: a mill that leaves the same player on the clock for the removal keeps the clock running, because the clock is per turn (GDD §5.3) and the removal is part of that turn. Two other places stamp it, and both start a turn rather than continue one: `/join` (the clock starts when the game can be played) and `/rematch` (a new game). Nothing else does — an *ending* is not the start of a turn, so a forfeit, an agreed draw and a resignation all leave the stamp where the last turn put it. `/claim-timeout` used to move it, on the theory that it stopped a claim being replayed; the finished-game check is what does that, and a mutation test found the stamp was unobservable prose. Each of the three endings now has a test that fails if it starts stamping, named so the claim can be checked: the forfeit in `clears a standing draw offer when it ends the game`, the agreed draw in `offers, then agrees when the other player answers`, and — added after a critic found the sentence was true of only two of them — the resignation in `leaves the clock where it was when a resignation ends the game`, which kills both `action.type === 'resign' ? now` and `game.result !== null ? now`.
- **State-conflict refusals are 409 even where the endpoint table only lists 403/400/404.** Claiming a timeout with no timer, or before it expires, or on a finished game; offering a rematch mid-game; offering a draw after the game is over — all are "your request is fine, the room is not in a state for it", which is what 409 means. The client can act on them (re-poll and re-render) exactly as it does for a version conflict.
- **A draw offer lapses when either player plays.** `/action` clears both `drawOffer` flags. Otherwise an offer made in the opening could be accepted forty moves later, when the position — and the offerer's mind — has changed. Offering twice is a no-op, not a self-acceptance. *Both* flags, including the mover's own: `/draw` has no turn check, so the player on the clock can offer and then play on, and an offer that survived its own author's move would turn the opponent's next plain tap into an agreement about a position nobody offered a draw in. `lapses the mover own offer, not only the opponent one` is the half that was prose until a critic asked for it.
- **Idempotent offers do not burn a version.** A mutation may return `null` for "nothing to change", and `mutateRoom` then answers 200 with the room as it stands and no write. Repeating a rematch or draw offer therefore leaves `version` alone, so the other client's polling does not see a change that isn't one.
- **`/join` takes an empty body and always claims Black.** It has no token to check — the joiner does not have one yet — so a creator whose client calls `join` again would take the second seat. That is a client bug, not an attack: the seats are only worth holding one at a time, and adding a token to the join body would put a credential on the one request that exists to issue one. Concurrent joiners are resolved by the store: one wins, the other re-reads and gets a 409.
- **The API reaches the store through `apiStore()`, with a `setApiStore()` seam.** `getStore()` returns a memoised instance, so a test cannot get a fresh store without a seam somewhere. The seam lives in the API layer rather than in the store, is used only by tests, and defaults to `getStore()`.
- **Player tokens are 16 crypto-random bytes as 32 hex characters** (`newPlayerToken`, which this item added to `src/lib/store/ids.ts`). `endpoints.test.ts` collects tokens in the wrapper that records every response, not by hand at each call site, so a test that forgets to register one cannot exempt it from the `afterEach` sweeps — but those sweeps pin only the *shape*, and a critic showed what that leaves open: `TOKEN_SHAPE` matches a constant as happily as a random token, and the leak sweep deletes the caller’s own token before it scans, so the same string recurring across rooms is invisible to it. Replacing `/join`’s `newPlayerToken()` with a fixed 32-hex string left the whole suite green — and a Black token issued in any room would then have seated its holder in every room. Distinctness is the assertion that catches that, and it covered only the create side, because the fifty-room loop never joined. `issues a distinct 32-hex token per seat, and a distinct id, per room` now joins each of its fifty rooms as well as creating it and requires a hundred distinct tokens, so both issuing endpoints are pinned. What still fails no test is “crypto-random”: a counter rendered as 32 hex characters would satisfy every assertion here, and only reading `newPlayerToken` says otherwise. A token is a bearer credential, so it is much longer than a room id and drawn from the full byte range rather than the human-readable alphabet: nobody ever reads one aloud, it lives in `localStorage`. `seatOf` is the only place a token is compared, and it compares with `===` and nothing else — pinned by `403s a token that is only nearly a real one, on either seat`, which rewrites the room's seats to long mixed-case tokens (32 lowercase hex characters are too short to slice and have no case to flip) and probes each seat with a strict prefix, a strict superstring, the same token upper-cased, one sharing its first eight characters, and — added after a critic pointed out that the sentence overstated what was pinned — the token with a space in front of it and the token with a space after it. Until that pair existed, `token.trim() === room.players.W` survived the whole suite: it reads as defensive tidying and every other probe on the list is immune to it. A padded token still requires holding the secret, so this is a claim about the comparison rather than a hole anyone could walk through, which is why the critic filed it as an overstatement and not as a defect. A stranger token proves nothing here: `not-a-token` is rejected by `startsWith`, `includes`, a case-folded compare and a prefix compare alike.
- **An empty request body is read as `{}`.** So a `POST` with no body works where the body is empty (`/join`) and fails validation where it is not (a missing token is a 400). A body that is not JSON is a 400, never a 500.
- **`timerMs` is optional at creation and defaults to 5 minutes** (GDD §5.3); `null` is the "None" choice and is not the same as omitting it. The four are asserted by value — `null`, `60_000`, `300_000`, `86_400_000` — rather than by iterating `TIMER_CHOICES`, which would only say the API accepts whatever that constant happens to hold. Under `MORRIS_E2E=1` any positive timer is also accepted, so the timeout e2e (GDD §8, bar item 3) does not have to wait out the shortest real choice; a timer outside the four choices is a 400 otherwise, and a negative one always is. **The flag is inert wherever Vercel runs the code** — the whole condition is `VERCEL === '1'`, which covers `vercel dev`, preview, production and the build. §8.3 sanctions the flag as test-only, and left ungated an operator who set it on a deploy would let any client open a room with a one-millisecond clock and claim an instant forfeit against whoever joined. One variable and no carve-outs: a client request never arrives during a build, so the build phase needs no exception, and any exception here would be a second environment variable — editable in the same dashboard as the flag — that turns the first one back on. `VERCEL` is trimmed before the comparison and `MORRIS_E2E` is compared exactly, so a padded value fails closed either way. (An earlier version of this bullet justified the predicate by comparing it to the store's; that comparison was falsified by a change over there. A comment about another module's internals is a liability — this one stands on its own reason.)
- **The clock starts when the second seat is claimed, not when the room is made.** `/join` restamps `turnStartedAt`. GDD §5.1's flow is create, share a link, then wait for the first other visitor, and with the default five-minute timer (§5.3) a creator's clock would otherwise expire while the link sat unopened in a text message — handing the win to a friend who arrived late without a move being played. The stamp does not consult `timerMs`: a timerless room is restamped too, pinned by `stamps the join even when the room has no timer at all`, because `turnStartedAt` is what every later turn is measured from and one rule is cheaper than one rule per timer setting.
- **A room waiting for its second player accepts nothing but a join.** `requireBothSeats` shuts `/action`, `/draw`, `/rematch` and `/claim-timeout` until both seats are filled — a resignation included. GDD §5.1 has play proceeding after the join, and a lone creator shuffling pieces would hand an arriving friend a position they never saw played, on a clock that had been running for a seat nobody held. It also keeps the pre-join room in exactly one state, which is what makes the clock rule above a one-liner.
- **A forfeit is never awarded against an empty seat.** `/claim-timeout` runs `requireBothSeats` before it looks at the clock: GDD §5.3 gives the win to the *opponent* of the player who ran out, and an unclaimed seat is neither. It is a separate guard from the clock starting at the join — starting the clock later does not help a room nobody ever joins.
- **A busy room is not a full one.** After `/join` exhausts its retries it re-reads before naming the failure: `both seats are taken` only when `players.B` really is set, and otherwise a plain version-conflict 409. Every 409 from `/join` carries the current `PublicRoom`, so a client told "full" can see the seats for itself. The seated player moving bumps the version too, so mapping any conflict onto "full" would have told a joiner the room was full while the seat sat empty.
- **`expectedVersion` is compared before the mutation runs, not only at write time.** `mutateRoom` rejects a stale action with a 409 before it judges the turn or asks the engine anything. Otherwise the dropped-response retry — the same move resent after a flaky mobile request — comes back "it is not your turn" (403) or "point 0 is occupied" (400), and the client is told its *action* was wrong when what it needs to hear is that its *board* is old. GDD §7.3 lists the 409 and the 403 side by side without ordering them, and the credential is the one exception to “version first”: `mutateRoom` resolves the token to a seat *before* it compares the version, so a request that is both stale and from a stranger is a 403. Telling a caller whose token holds no seat to resync and retry would send it round that loop for ever — no version it adopts gives it a seat. Both directions are pinned by `403s a stale action from a stranger, and 409s the same one from a player`; before it, moving the version block above the `seatOf` check left the suite green.
- **A refusal carries the room whenever the server had one to attach.** Every 403 and 409, and the 400 the engine raises for an illegal action, come with the current `PublicRoom`, so a rejection is also a resync. Three do not: a 404, where there is no room; the 400 a malformed body earns, which `parseBody` answers before any room is read — a client that sent unparseable JSON has a bug, not a stale board; and the 500 for an unrecognised failure, which carries nothing but `error`. When a write conflicts and the room is not there on the follow-up read the answer is a 404, not a 409 about a version nobody can fetch. `endpoints.test.ts` asserts the presence for every 403 and 409 the suite provokes — the route handlers are wrapped so that every response is swept, read or not, which an inline `expect(status).toBe(403)` used to escape — pins both halves of the 400 by name, and reaches the vanished-room path with a store whose every write loses.
- **A finished game is a 409 everywhere, including `/action`.** It used to be the engine's `IllegalActionError` → 400 there while `/draw` and `/claim-timeout` called the identical state 409. One rule: the request was fine, the room is not in a state for it.
- **Every rematch swaps the colours, not just the first.** `/rematch` swaps `players` unconditionally when both sides have tapped, so which person holds White alternates with `gameNumber` — the parity the client reads back. Tested through a second rematch (`swaps the colours again on the rematch after that`): a swap that only fired on the first reset would leave the creator as Black for ever from game 2 on, contradicting GDD §5.4 and §7.4, and one game of rematch cannot tell the two apart. That test is pinned for *resignations*, and for a round that was the only ending the suite ever showed `/rematch`: both of its games end in one, so `players: room.game.result?.reason === 'resign' ? { W: room.players.B, B: room.players.W } : room.players` left the file green — the colours stopped swapping after a mill-out or a win on time, which is how real games end. `resets the room, whatever ended the last game` now runs the whole reset after a resignation, a win on time, a mill-out and an agreed draw, each played for real, and `a finished game, whatever finished it` runs it after all six reasons the engine can end on.
- **`/draw` and `/rematch` are shut before the second seat is claimed, like `/action`.** A flag set by a creator alone would otherwise still be standing when a visitor arrived, and that visitor's *first* tap on "Offer draw" — or "Rematch" — would silently be an acceptance of an offer they never saw. Shutting the endpoints beats clearing the flags at the join: there is then no window in which a half-agreed state exists at all.
- **No room can reach a state with no legal action for anybody, and a test walks it.** An earlier pass let a lone creator resign and then had `/join` refuse the decided room: one tap destroyed the link for good, with `/rematch` refusing forever because it needs two seats. The root fix is that a waiting room takes no mutation at all (above), so a game cannot be decided before it has two players — and with that, `/join`'s decided-room refusal was deleted rather than kept as dead code. Had it stayed and the state somehow occurred, it would brick the room again; without it, a joiner seats and can always rematch. `endpoints.test.ts` walks waiting → live → over → rematched and asserts something is open at each step.
- **`/claim-timeout` clears `drawOffer`.** `/action` clears the flags on every move and `/draw` clears its own when it ends a game, which left the forfeit as the one ending that could leave an offer standing — a finished board still rendering "Black has offered a draw".
- **`PublicRoom` differs from the stored `Room` by three fields added and two withheld, and a test computes that rather than trusting this sentence** (`differs from the stored room by exactly three fields, and drops two`). Added: `seats`, which reports which chairs are filled *without* the tokens that fill them and is where the narrowing actually happens; `serverNow`; and `clockRunning`. Withheld: `players` — the tokens — and `createdAt`, which no client has a use for. `serverNow` came with the contract as handed to this item: the client counts the turn down from `serverNow - turnStartedAt` rather than from its own clock, so a device with a skewed clock still shows the right number and the server stays the only timekeeper (GDD §5.3). `clockRunning` is the one field this item added to `PublicRoom`; `seats` and `serverNow` came with the contract, and the only other change this item made to the contract file was deleting the unused `ActionRequest` (below). `turnStartedAt` is stamped at creation (GDD §7.4 types it `number`, not `number | null`) but the clock does not really start until the second player joins, so a client drawing the §5.3 countdown from `turnStartedAt` alone shows a creator's timer draining below zero while the room waits. `clockRunning` is true only when both seats are filled, a timer was chosen, and the game is live: draw the countdown when it is true, and nothing when it is false. Inferring that from `seats.B` would be a rule the contract never stated.
- **The API tests run on a frozen clock.** `Date.now` is stubbed per test and moved by an explicit `advance()`; every action spends a second of thinking time. Wall time made "the clock restarted at the join" unprovable when two requests landed in the same millisecond — a real flake, seen once — and it is the wrong tool anyway: the assertions want exact arithmetic, not "greater than, probably".
- **One guard order, in all four mutating routes.** The body's shape, checked by Zod in the route's own `parseBody` before anything is read, then the credential and the version — those two are `mutateRoom`'s, before any route's own callback runs — then `requireBothSeats`, then which *game* the tap was about (`/draw`'s `gameNumber`, the only one), then the game's state, then the route's own rules — which for `/draw` means the `accepting` check, deliberately after the state so that a finished game is answered as a finished game rather than as a stale offer (`/action`'s refusal of a client-sent `forfeit`, then whose turn it is), then the engine. The order is what stops one room state producing two different explanations: `/rematch` used to answer "waiting for an opponent" where `/draw` answered "the game is over", and `/action` used to answer a forfeit on a finished game with 403 where every other action got 409.
- **A 409 means the room moved on, not that the board did.** Any write bumps `version`, so an opponent's draw offer can make an in-flight action stale although the position is untouched. `ApiError`'s doc comment says so, because the online client will re-send on a 409 and must not draw a conclusion about the board from it. Nor is 409 the only refusal a lost race produces: when a move beats a timeout claim it restamps the clock onto the claimant's own seat, so the retried claim comes back **403** `the clock is yours; only your opponent claims it` — true of the room as it then is. The 40-round race test pins both, by kind, so a client that handled only the 409 would be wrong in half the orderings.
- **The `clockRunning` test asserts the invariant, not a list of states.** Across ten room states it checks that the field is true exactly when nothing but elapsed time stands between the player off the clock and a successful claim — so a state nobody listed is covered by the same test, as far as the *moment* the view is read from. For a round it was read before the two-day advance that made the claim possible: one moment's answer judged against another moment's claim, and adding `now - room.turnStartedAt <= room.timerMs` to the conjunction therefore survived. Under that version the field goes false the instant the clock runs out, so a client following the field's own contract stops drawing the countdown and hides "Claim win" exactly when the win becomes claimable — and with no auto-forfeit (§5.3) an abandoned game then deadlocks for ever. The view is now read *after* the advance, in the same moment as the claim, and that mutant fails four of the ten states. The hostile-body matrix is the same idea for input: six endpoints × nine malformed bodies, with the expected status *derived* from what each endpoint's body must contain.
- **Every response the route handlers produce carries `Cache-Control: no-store`, set in `jsonResponse`.** `dynamic = 'force-dynamic'` governs Next's own build and data caches, not HTTP caching: a real `next start` answered the polling `GET` with no cache directive at all, leaving a browser or intermediary free to apply a heuristic to the endpoint every client hits every 1.5 s (GDD §7.3). One header, in the one function every route answers through, asserted in the suite and checked against a production server. What it does not cover is whatever the framework answers when no handler runs. Measured against `next start`, on every route alike (all seven are `force-dynamic`; there is no static one): an unexported method is a 405 with an empty body, a preflight is a 204, and `TRACE` is a plain-text 500 — the App Router has no `TRACE` handler to export, so that one cannot be answered by this code at all. `HEAD` on the polled `GET` *is* covered, because the framework derives it from `GET`. None of these is a request this app makes; the `TRACE` 500 does mean an unauthenticated caller can push errors into a deploy's error rate, which is noise in a dashboard rather than a way to touch a room.
- **`ActionRequest` was deleted, not re-derived.** The hand-written interface in `types.ts` had no importer — the route validates with `actionRequestSchema` and the client builds the body inline — and had already drifted from the schema (`expectedVersion: number` against `z.int().nonnegative()`). Deriving it from the schema would only have moved a dead export, so it is gone: `actionRequestSchema` is the one definition, and `z.infer` of it is there for whoever first needs the type.
- **Every refusal this API authors lives in one table, `REFUSAL`** (in `refusals.ts` — see the bullet on that file below; it began in `handlers.ts`). It includes the message Zod carries for a timer that is not one of the four — a refusal this layer authors as much as any other, and one that used to sit outside the table. (No count here: the test compares the whole table to its English, which is the assertion that keeps it honest.) Most of them began as literals repeated between a route and the suite — `'the clock has not expired'` four times over — which is why the table exists. Every route throws them by name, `endpoints.test.ts` asserts them by name, and `e2e/timeout.spec.ts` imports the table too. The English is written out again in the one test that pins the table, and in a handful of test titles — copies a change is supposed to break. One sentence exists outside the table as well: the engine's `apply` throws `'the game is over'`, the same words as `REFUSAL.gameOver`. They are two different refusals that happen to read alike, and only ours can reach a client: every route checks `result` before it calls the engine, so the engine's version of that message is unreachable through the API.
- **A store failure this layer does not recognise is a 500 that still looks like the API.** `guarded` wraps all four places that touch the store — `mutateRoom`, `readRoom`, `/join`'s retry loop and the straight-line room creation in `POST /api/game` — and turns anything unrecognised into `{"error": "the server could not complete that request"}` with the `Cache-Control` header. Without it a `CorruptRoomError` (which the store really raises) escaped into the framework, and the client got an HTML-ish 500 with no `error` field to read. The thrown message never goes on the wire — it can name a key or an id — and is logged instead, one line, with the error's name.
- **The 409 for a client that pinned no version is worded by us, not by the store.** `VersionConflictError`'s sentence names the version the caller sent, which `/action` did and `/draw`, `/rematch` and `/claim-timeout` did not: those used to answer "Room RRD4CCPT is at version 3, not 2" to a client that had never mentioned version 2. They now say `the room changed while writing; try again`. `/action` still gets the store's sentence, because there it means something.
- **The API layer is at 100% statements, branches, functions and lines**, which `npx vitest run src/lib/api --coverage.enabled --coverage.include='src/lib/api/*.ts' --coverage.include='src/app/api/**'` prints (no counts quoted here: a number in prose is a claim that goes stale on the next line of code). The table it prints includes an `index.ts` row of zeroes — the barrel re-exports and has no executable statement to cover. The last four uncovered branches were the `RoomNotFoundError` → 404 on both write paths, the honest `both seats are taken` after a lost race, and a store that throws something that is not an `Error`; each needed a store that fails in a particular way, which is why `endpoints.test.ts` carries three small fake stores.
- **Four behaviours were held up by prose alone until a mutation test found them, and each now fails at least one test.** Deleting `turnStartedAt: now` from `/rematch` (a rematch begun two minutes after the banner appeared started already lost on time — a win awarded for nothing; pinned, until `resets the room, whatever ended the last game` existed, by a single test whose previous game ended in a resignation, so `turnStartedAt: room.game.result?.reason === 'resign' ? now : room.turnStartedAt` produced that consequence word for word after every *other* ending and left the suite green), dropping `86_400_000` from `TIMER_CHOICES` (which fails *two*: `offers exactly the four timers of GDD §5.3, by value` and the fuzz run, which seats every one of its games on the day-long timer — the other three fail exactly one, and "exactly one" was the count this bullet used to claim for all four), changing `<=` to `<` on the claim comparison (which decides the instant of expiry, the case GDD §8.2 leaves undecided between "before" and "after"), and removing `drawOffer: { W: false, B: false }` from `/draw` all used to leave the suite green. The lesson kept for the rest of the build: a line whose deletion breaks nothing is untested however many tests surround it, and the four here were each one line away from a wrong result on the wire.
- **A fuzz run stands guard over the one rule the whole design rests on.** Thirty sessions of sixty steps, deterministic seed, each step choosing between a legal action and nonsense: every accepted response must equal `apply(before, action, seat)` exactly and bump the version by one, and every refusal must leave the stored room byte-identical and stay under 500. It asserts its own coverage — hundreds of accepts, hundreds of refusals, and hundreds of steps *in the movement phase*, without which a session that never empties both hands would be testing a third of the rules. It costs about 150 ms and it kills a mutant that nudges the server's state a single field away from the engine's.
- **The critic's pairwise 7×7 race matrix was not adopted.** The races that can actually interleave two writers on one room are already pinned: claim-versus-move in both orderings (which is where the interesting restamp lives), simultaneous rematch, simultaneous join, and a store that loses every write. A full matrix would mostly re-exercise the version-conflict path those already cover, for several seconds of runtime on every `npm test`.
- **These lines were load-bearing with nothing watching them, and each now fails a test when weakened.** In order: `/draw` *not* restamping the clock (the mirror of the `/rematch` mutant from the round before — under it the player on the clock could reset their own by tapping Offer draw); a wrong-turn `remove`, which §4.5 makes a sub-step of the turn and which fell through to a 400 where §7.3 says 403; a draw offer surviving the half of a mill turn that keeps the same player on the clock, so the miller's own next tap would *accept* an offer made against a different position; `serverNow` on the idempotent no-op 200, which the client draws its countdown from; `timerMs: 0` on both sides of the e2e flag; the wording *and* the field name of the timer refusal, where a `toContain('timerMs')` passed on the field name alone; a rematch carrying a standing offer into the new game; a negative or fractional `expectedVersion`; a fractional board point; the retry budget on the shared write path, which was bracketed only from below (`/join`'s own budget went unbracketed for two more rounds — see below); a whitespace-only body; and the two seat-W conjuncts. The pattern behind most of them: a test that asserts a substring, or asserts through a path where the value under test happens to be the same either way.
- **A state the API cannot produce can still be written into the store and tested.** The two `players.W` checks are unreachable through any endpoint — seat W is filled at creation and only ever swapped for a non-null B — so rather than leave them as untestable defence, the suite writes such a room with `store.set` and asserts what the guards do with it. Same technique for a rematch inheriting a standing draw offer. It is the honest middle between deleting a guard the types still allow and keeping one that nothing exercises.
- **The critic's probe suites were read and not adopted.** They are instruments — `console.log` of a status and a body, with assertions added afterwards — and they carry their own harness, so adopting them would have meant a second set of helpers and, more to the point, tests that skip this suite's global sweeps for token leakage and refusal shape. The twelve cases they found are pinned here instead, in the harness that sweeps.
- **`POST /api/game/[id]/draw` takes an optional `gameNumber`, and refuses a tap made about another game with a 409.** Accepting a draw is a decision about a position (GDD §4.6), and it was the one mutation with nothing tying the tap to the board the player saw. A page that stopped polling — §7.3 stops on a hidden tab — keeps an "Offer draw" button alive across the end of that game and a rematch, and one tap on it agreed a draw in a game that page had never displayed. `/action` was never exposed to this: `expectedVersion` is a strictly stronger pin, since every write bumps the version. The field is optional, so a body without it is judged exactly as before; when it is present and does not match, the room comes back with the refusal and the tap is lost like any other lost tap. It is checked after `requireBothSeats` and before the game's state — a room still waiting for its second player is not playing any game to be stale about, while a room that has moved on to another game would answer every later question about the wrong position. Both directions are pinned: moving the check either way changes an answer a client can see. The comparison is equality and not "no earlier than": a `gameNumber` *ahead* of the room is as wrong about the position as one left behind, and `refuses a tap about a game the room has not reached either` says so on a seated, live room — the only place that answer is reachable, since a room with one seat is refused by `requireBothSeats` first.
- **`/rematch` and `/claim-timeout` deliberately do not get the same field.** The asymmetry is what a stale tap can *do*. A stale draw ends a live game — irreversible, and half a point taken from a player who never saw the position. A stale rematch cannot: the server already refuses a rematch into a live game, so the only tap that lands is one on a finished game, and its worst outcome is a rematch the player asked for a moment earlier than they meant — the button means "play again" in every state where it is accepted, and it takes two players to fire it. A stale timeout claim only succeeds if the opponent's clock really has run out on the *current* game, which is an entitlement the claimant has whether or not they knew it. Neither is worth a second staleness field on the wire, and each field a client must remember to send is a field it can forget.
- **A client may pin `gameNumber` on any tap; only `/draw` honours it, and that is deliberate.** `/rematch` and `/claim-timeout` share a schema that strips keys it does not know, so the field is accepted and ignored there rather than refused. Rejecting it would turn an additive change into a 400 for a client that pins everything out of habit, and honouring it would buy nothing: a stale rematch can only start a game and a stale claim only succeeds against a clock that has really run out. The asymmetry is now a test on `/rematch`, so it is a decision rather than an oversight — but it is a real asymmetry, and the online client should send the field only where it means something.
- **Room ids are matched exactly, case and surrounding whitespace included.** A lower-cased id 404s on the read and on every write, and so does a padded one: nothing trims. Folding case in `readRoom` alone would make the poll succeed where every action still failed; folding it everywhere is a change to the six routes that take an id, for a way of reaching a room that GDD §5.1 does not describe — the id travels in a link, and `ids.ts` already keeps the alphabet unambiguous so that link cannot be mistyped into a different room. “Every write” means each of them, probed one route at a time: the six id-taking handlers destructure their own `id`, so this is a per-route property, and a probe aimed at `/draw` says nothing about `/action` — where a `.trim()` survived the whole suite until a critic tried it. `matches a room id exactly, case and whitespace included` now runs its lower-cased and padded probes through `/action`, `/rematch` and `/claim-timeout` as well as `/draw`, each with a body valid enough that a 400 cannot stand in for the 404 and on a room where a resolved id would answer 200, 409 or 403 instead. `/join` is the seventh probe and was the last hole: it is the only id-taking write with no token, so it is probed on a room that still has a free seat — and it used to be probed with **padded ids only**. Padding survives `toUpperCase()`, room ids are already uppercase, and so `claimSeat(id.toUpperCase())` left the whole suite green while `POST /api/game/<lowercased>/join` seated a player in the real room: a 200 and a claimed seat where every other route 404s. The lower-cased probe is now there too, and each of the three asserts `players.B` is still `null` afterwards, so a 404 that seated somebody anyway would not pass either.
- **More of the same the round after, each now failing a test when weakened.** The one with teeth: `expectedVersion` is passed to `mutateRoom` untouched, and `expectedVersion === 0 ? null : expectedVersion` — a plausible-looking "treat zero as absent" — would have made a client's move skip the staleness check entirely, because `null` is the sentinel for "pinned nothing". The rest: `serverNow` on the three refusal bodies not built by `view()`, now covered by one sweep asserting that every room the server hands out is stamped with the moment it was made; the shape of a validation message (which field it names, how several are joined, that a complaint about the whole body arrives without an empty label); the position of the `gameNumber` guard in both directions; the `expectedVersion === null` half of the retry rule, so a pinned write is not retried; `guarded`'s log line, which is the only way an operator learns why a room broke; `createdAt`; `z.int()` on `timerMs`, which is only load-bearing under the e2e flag; and that `/action` tolerates unknown keys like every other endpoint.
- **`POST /api/game/[id]/draw` also takes an optional `accepting: boolean`, and the server decides which of the two things the tap was.** `gameNumber` closed the cross-game window; this closes the same-game one, which is nastier because it is correlated: two players reach for a draw in a drawn-looking position at the same moment, the opponent's offer lands *inside* this request, and the same body then means "offer" to the player who sent it and "accept" to the server. GDD §4.6 ends a game only "if the other accepts", and that player accepted nothing. `accepting: true` means "accept the offer I can see", `false` means "make one"; the server compares it with the opponent's flag *at write time* and refuses a mismatch with 409 `that was about a different offer`, carrying the room. Both directions matter: an acceptance of an offer that has since lapsed must not quietly become a new offer either.
- **`accepting: boolean` rather than echoing the `drawOffer` pair.** The pair is more literal about what was on screen, but it carries a bit that is not part of the decision — the caller's own flag — and a disagreement there is harmless (offering twice is already a no-op), so echoing it would produce refusals for taps that are perfectly good. One bit that names the intent refuses exactly the taps whose meaning would change, and it is the same bit the button's label was chosen from.
- **A client no longer needs to read before it writes to make a draw tap safe.** With `gameNumber` and `accepting`, what the tap claimed about the room is judged inside the same write, under the same optimistic-concurrency guard as everything else — a read beforehand can narrow that window but never close it, and this closes it. What the online client does with that is the online item's call, not this one's.
- **`REFUSAL` lives in `src/lib/api/refusals.ts`, a module with no imports at all.** The client has to tell "this server says the room is gone" from "a middlebox returned a 404 with a JSON body" — a poll that believed the wrong one ended a live game with no recovery but a reload — and the only honest test is comparing the message with the one this server would have sent. It could not import `@/lib/api` for that, because the barrel reaches `handlers.ts` and through it the store. The table is still exported from `@/lib/api`, so nothing that imported it before changed; a browser can import `@/lib/api/refusals` instead. The property is "this module's dependency closure is empty", and the test now *parses* the file with the TypeScript compiler and asserts the parser finds no module specifier of any kind — import, `export … from`, dynamic `import()`, `require()` — with the exported names checked to be exactly `REFUSAL` as a second net. A module with no specifiers has an empty closure by definition, so there is nothing further to walk.

  It took three attempts to get there, and the two failures are the point. The first checked `/^\s*import\s/` and let a re-export through — one line, and `@upstash/redis` shipped to every visitor through a `'use client'` importer. The second stripped comments with a regex and was beaten by a string literal holding `/*` before the import and one holding `*/` after it: all gates green, the store in the browser chunk. **A regex cannot decide this question**, because deciding it means knowing which text is code, which is what a parser is for. The general lesson, now paid for twice: when a test asserts a property of a *language*, the language's own tools have to be the ones asserting it. Whether anything in the browser actually imports it is the online item's business; this side only guarantees that it *can*.
- **Two endings could have left the engine behind, and the suite would not have noticed.** GDD §7.3 says all mutation goes through the engine, and both endings did: `apply` with a `forfeit` action for the timeout, and `agreeDraw` for the agreed draw — which §7.1's five-variant `Action` union has no way to express, so `/draw` cannot call `apply` at all. But the only fields any test read back from those two responses were `result` and `phase`, so a hand-built `{...game, phase: 'over', result}` passed everything. It is visible to a player: form a mill, walk away, and a forfeit claimed while the removal is still owed leaves `pendingRemoval` set, so the client draws removal mode under a game-over banner. Both endings now assert the *whole* `game` equals what the engine returns for that ending, with the mill case set up so `pendingRemoval` is true going in.
- **A duplicated pure guard was invisible to every gate this project had, until one was built for it.** A second `requireBothSeats(room)` changes nothing observable: the suite, `tsc` and `eslint --max-warnings 0` all stayed green, which is exactly how one survived a whole round here. The only cheap catch I found is to assert the count against the source text, so `applies the seat guard exactly once in /%s` now reads each of the four mutating routes and requires the guard to appear once. It is a lint rule wearing a test's clothes, and it is worth it only because the failure mode is silent, real, and already happened once.
- **`/draw`'s intent check runs before the idempotency short-circuit, and that order is now pinned too.** Repeating your own offer is a no-op; claiming to *accept* when the only offer standing is your own is not the same request, and answering 200 to it would report an acceptance that never happened. The reachable case is the second tab §5.1 supports: the tab still shows "Accept draw" from an offer that has since lapsed, while its owner's own offer is what is standing. There are **four** places the intent check sits relative to, not three — the seats, `gameNumber`, the game's state, and the no-op — and this bullet used to claim all of "three" were pinned when only the state and the no-op were. Hoisting the check above `requireBothSeats` *and* above the `gameNumber` guard, guarded so that only the live-game case moved, left the suite green, and two answers a client can see changed with it: a lone creator posting `{token, accepting: true}` was told `that was about a different offer` rather than `waiting for an opponent to join`, and a tap naming another game was told the same rather than `that was about a different game`. The waiting-room loop sends `/draw` with `accepting: true` now, and `refuses a tap about a game the room has not reached either` names a `gameNumber` the room has not reached *and* an offer that is not standing — one word each, and all four orderings are pinned in both directions.
- **The write pins the version that was read, and says so.** `store.update(id, …, room.version)` replaced `expectedVersion ?? room.version`: the pre-check has already answered 409 for any other value, so the two were equal by construction and the `??` only read as though the client's pin were being re-asserted at write time. It is not; what guards the write is the store re-checking that version. Behaviour is identical, and pinning any other version there fails a large part of the suite rather than passing quietly (no count: a number in prose is a claim that goes stale on the next line of code). The line no longer implies a check it does not make.
- **A 409 from a lost write re-reads the room before handing it back.** Handing back the room the caller read — the one that lost, by definition — would tell the client to re-send pinned to a version the server has already moved past, so the re-send would conflict again: a resync that does not sync. Both paths are now pinned by asserting the refusal's `room.version` equals the store's version at that moment, on `/draw` (three lost races, the retrying path) and on `/action` (one lost race, pinned so the pre-check passes and the conflict happens at write time). The earlier tests could not see this: they asserted `id` and `seats`, and the fake store they used returned an unchanged room, so the stale and fresh values were equal by construction.
- **`/join`'s retry budget is now bracketed from both sides, separately from the shared one.** It runs its own loop with its own counter, so the `mutateRoom` test that pins three attempts says nothing about it; a store that loses exactly three races now proves a fourth attempt would seat a joiner who should have been refused, and losing one proves the budget cannot shrink either.
- **Four more load-bearing lines, found by mutating them and watching nothing go red.** `id: newRoomId()` in `POST /api/game`: replacing it with a constant left the whole suite green at 100% branches, and `RoomStore.set` is create-or-replace, so a repeated id would silently overwrite a live game — two pairs of players on one URL, with the first creator's token still holding seat W in the room that replaced theirs; the id set is now collected across the same fifty rooms as the tokens. `move.to` and `remove.point` in `actionSchema`: widening either to accept a string still answered 400, because the engine's `Number.isInteger` guard catches it downstream — the status was right and the schema's own contract was unenforced, so the two cases now assert *which field* the refusal names. The nested half of the validation message: every assertion used a depth-1 path, so `issue.path.join('.')` could have been `join('/')`, the first segment alone, or the last, and none of the three would have failed; a `move` missing `to` now has to say `action.to: …` exactly. And the room id reaching `readRoom` and `claimSeat` untrimmed — "matched exactly" had only case behind it. Eight mutants in all, each of which now fails at least one test.
- **`/claim-timeout` judges the seats before the game’s state, and that order is now pinned.** Moving `requireBothSeats(room)` below the finished-game and `timerMs === null` checks left the suite green: the `clockRunning` invariant test walks a lone creator on a timerless room but asserts only `status === 200`, and `mentions the missing timer before whose clock it is` used a seated room. Under the mutant that creator is told `this game has no turn timer` — an explanation about a game nobody is playing — where the true answer is `waiting for an opponent to join`. The same test now asserts the waiting room’s answer as well, so the guard order in this route is pinned by more than the shared prose in `One guard order, in all four mutating routes`.
- **Four more orderings and two derived values, each of which used to leave the suite green.** They are collected here because they are one failure repeated: a guard whose *position* is the behaviour, or a value the route derives, tested only through the one arrangement where the wrong answer happens to look right. That sweep stopped at *position*, and there is a second axis to the same thesis: not where the guard sits but **which seat is asking**. Restricting a guard to one seat (`&& seat === 'W'`, then `'B'`) is the same experiment, and the last two sub-bullets are what it found.
  - **`/claim-timeout` forfeits the player who is actually on the clock, claimed by the seat that actually sent it.** `apply(room.game, { type: 'forfeit', player: onClock }, seat)` — every successful claim in the suite had White on the clock and Black claiming, so `onClock` could be the constant `'W'` and `seat` the constant `'B'` and nothing went red. Against *Black's* expired clock the constant makes `applyForfeit` throw `only the player on the clock can forfeit` and the claimant gets a 400 instead of the win, so GDD §8.2's "accepted after" held in one direction only. `awards the forfeit against Black's clock, claimed by White` is the other direction, and it kills both constants.

White resigns — the turn stays White's — and Black's plain `place(0)` is out of turn as well as too late; the answer is the 409, and `409s a forfeit on a finished game, like every other action` now says so for a plain action too.

The forfeit is in the waiting-room loop now.

(1) `/action`'s wrong-turn 403: every out-of-turn probe in the file is Black acting on White's turn, so `&& seat === 'B'` cost nothing — and under it a White caller whose poll is one tick behind falls through to `apply()` and gets the engine's wording as a 400 where §7.3, and the `Wrong turn is a 403` bullet above, say 403. ## Hot-seat (gauntlet item 6)

- **A rematch swaps which *person* plays which colour, tracked by `gameNumber`.** GDD §5.2 says "Rematch swaps colours" and §9 says White always moves first, so on one device the swap cannot be a change to the board or to who starts — it has to be a change to who is holding which colour. `/local` therefore keeps a 1-based `gameNumber` (the same field, with the same parity rule, as §7.4's room) and derives `Player 1`/`Player 2` → colour from it in `src/app/local/seats.ts`. Game 1: Player 1 is White. Game 2: Player 1 is Black. The board, the engine and the first move are untouched.
- **The seat mapping is rendered, because otherwise the swap is invisible.** A line in the bottom bar reads "Player 1 plays White · Player 2 plays Black". Without it, a rematch in hot-seat is indistinguishable from a new game — every observable (White to play, nine in hand each, an empty board) is identical, and there would be nothing for the e2e to assert. It is also the only thing on the page that tells the two people which of them is up when the status bar says "White to play".
- **Resign and Agree draw are in hot-seat, as single taps, with no confirmation.** GDD §6.1 puts them in the bottom bar of the layout and §4.6 makes both real endings; on one device "resign" can only mean the player to move gives it up (`apply(state, {type:'resign'}, state.turn)`) and a draw offer and its acceptance are the same tap by two people sitting together (`agreeDraw(state)`). Both are one engine call. No confirm step: the GDD asks for none, a mis-tap is a Rematch away, and a modal is UI the GDD does not sanction. Both buttons disappear once the game is over, so neither can be pressed into a finished game.
- **No timer in hot-seat.** GDD §5.2 says the timer is optional there. It is not built: the clock is server-authoritative (§5.3, `turnStartedAt` on the room) and `/local` has no server by design, so a hot-seat timer would be a second, client-side implementation of the one thing the GDD says the server owns.
- **The game-over banner sits between the status bar and the board.** §6.3 asks for a banner with the result and the reason; putting it above the board keeps the final position visible (an overlay would cover the mill that just won) and keeps the page a single column that cannot overflow. It carries the Rematch button, because a finished game has exactly one thing left to do.
- **The placeholder "New game" button is gone, and nothing replaced it.** Rematch already resets to a fresh game; a second button that resets to a fresh game *without* swapping the colours would be a feature the GDD does not ask for (§5.1's separate "New game" link is the online flow's route back to `/`, which here is the Home link).
- **The banner reuses `statusHeadline` for the colour and the reason, and leads with the line the chrome cannot show.** "White wins — mill-out", "Draw — agreed" and the rest are `chromeModel`'s vocabulary; duplicating that reason table in `src/app/local` would have been the "never mirror" rule broken for two lines of JSX. But the status bar shows the same sentence for a finished game, so the banner puts *"Player 1 wins."* in the bold line and the colour-and-reason underneath in small type: the eye gets the new information first and §6.3's result-and-reason is still on screen, in one wording rather than two.
- **The scripted e2e game is a frozen literal, not computed.** `e2e/scripted-game.ts` holds a 32-action White mill-out found by self-play against the engine and then written down. Generating the moves from `legalActions()` at test time would test the engine against itself and could quietly stop reaching a mill-out; a literal that no longer produces "White wins — mill-out" fails the spec, which is what an e2e is for.
- **`e2e/helpers.ts` drives the board by `aria-label`, not by test ids.** The points are found as `Point 12, …` buttons (§6.5), which is the same handle a screen reader uses, so a regression in the accessible name breaks the e2e rather than passing unnoticed. The chrome is read by test id, because its text is the thing under assertion. Every helper takes a `Page`, so item 7's two-context spec can point them at two pages.
- **A two-tap move is synchronised on `aria-pressed`, not on a sleep.** `playActions` taps the piece, asserts the button reports itself selected, then taps the destination. There is no `waitForTimeout` anywhere in the suite and nothing depends on the mill flash or the removal pulse, both of which are decorative CSS.
- **The no-horizontal-scroll assertion was checked by making it fail.** `document.documentElement.scrollWidth - clientWidth <= 0` is only worth asserting if something can move it: a 900 px spacer temporarily added to `/local` produced `Received: 556` and a red run at 360 px, and the spacer was removed. There is no `overflow-x: hidden` in the CSS (it was removed in item 5) and none was added.

## Online mode (gauntlet item 7)
- **The seat is a token plus the game it was issued for, and the colour is derived.** `PublicRoom` deliberately carries no tokens (§7.3), so nothing on the wire says which seat *this* device holds — and a rematch swaps the colours attached to the two tokens (§5.4). `localStorage` therefore holds `{token, colour, gameNumber}` and `colourFor()` flips the colour on the parity of `roomId`'s `gameNumber` minus the stored one: each rematch increments it by exactly one and swaps exactly once, so the parity is the whole answer. The alternative — having the server echo the caller's seat — would have been a change to the wire contract, which is not this item's to make.
- **A browser that will not store a token gets a read-only board, not a seat.** `localStorage` can be missing or throw on write (private mode), and §5.1 is explicit that losing the token loses the seat. Claiming Black with a token that cannot survive a refresh would burn the room's only free seat on a tab that can never come back to it, so `storageAvailable()` decides: no storage, no join, spectate instead (§6.4). On `/` the same probe runs on the tap rather than on mount — it cannot change while the page is open, asking at the moment it matters keeps the server and first client renders identical, and it means the front door never creates a room its creator could only watch.
- **Every refusal is a resync, and nothing is ever a message.** The API attaches the current `PublicRoom` to every 4xx it can, so the client adopts the room out of a rejection exactly as it does out of a 200 and re-renders. A lost tap leaves no trace on screen (§6.2) — there are no toasts anywhere in this app. The one place a failure is truly invisible is a failed `POST /api/game`: the New game button comes back and nothing is said, because there is no error surface in the design to say it in.
- **`adopt` refuses to go backwards.** A room's `version` only ever climbs, so a response carrying a lower one is a poll that overtook a mutation. Without the guard, a 1.5 s poll in flight when a tap lands re-draws the board as it was before the tap — the exact "client trusts something other than the server's latest word" failure §7.3 is written to prevent.
- **The selected piece is derived, not stored.** A selection is only real while the engine still lists a move out of that point, so the board and `interpretTap` are handed `selectedNow`, filtered against the current legal list, rather than the raw state. Otherwise an update that arrives between the two taps of a move — the turn passing, a rematch resetting the board — leaves a selection pointing at a piece that is no longer there, and the fix would be a `setSelected(null)` in every path that adopts a room, one of which would eventually be forgotten. *(Overstated, corrected in the eleventh pass: the ring this describes is prevented three times over and `selectedNow` is only one of the three, so no single mutation of it is observable — `buildMarks` marks a point `selected` only when the legal list also makes it `selectable`, and `Board` emits `aria-pressed` only for a selectable point. What this derivation is still for is `interpretTap`, whose `selected` parameter is "the currently selected own piece": the page owns that input rather than borrowing a component's filtering for it.)*
- **One request at a time.** A ref, not the `busy` state, guards the write path: `setBusy(true)` lands a render too late to stop the second tap of a double tap, which would otherwise send two actions pinned to the same `expectedVersion` — the first winning and the second coming back 409. The dropped tap is silent, like every other ignored tap.
- **The poll interval is a pure function, and a missing room is not polled.** `pollIntervalMs({hidden, missing, live, yourTurn})` is §7.3's rule in one testable place: 1.5 s when the game is live and it is not your turn, 5 s otherwise, and `null` — do not poll — while the tab is hidden or after a 404. `useRoom` takes an `isYourTurn(room)` predicate rather than a boolean because only the caller knows which seat this device holds, and the hook must ask it about whatever room it is holding.
- **The client reads its own server's responses as declared, without Zod.** Zod guards the API's boundary because request bodies are untrusted (§8.6); the response to our own request from our own server is not the same class of input, and a second schema for every endpoint would be a copy of `types.ts` to keep in step. The client imports from `@/lib/api/types` and never from `@/lib/api`, so the store and `@upstash/redis` cannot follow the wire contract into the browser bundle.
- **Both clocks are drawn, and the idle one shows the full turn allowance.** §5.3 asks for "a countdown for both players" on a clock that resets every move, so the player who is not on the clock has nothing counting down — what they have is the time their next turn will start with. That is what their readout shows, in grey, while the active one counts and turns red under ten seconds. The countdown is drawn only while the room reports `clockRunning`; before an opponent joins, `turnStartedAt` is a placeholder and there is nothing to show.
- **Claim win appears half a second after zero, not at zero.** The server awards a forfeit only when the elapsed time is *strictly* greater than the timer, judged by its own clock; the client's estimate of that clock (`serverNow + skew`, corrected at each poll) can sit slightly ahead. `CLAIM_GRACE_MS` means the button appears when the claim will actually be honoured, so a player never taps it and watches nothing happen. Skew is measured as `serverNow - Date.now()` at each response, which ignores the response's flight time and therefore always errs late — the safe direction.
- **The countdown ticks at 250 ms and is display only.** No client-side timer ever ends a game: §5.3 says there is no auto-forfeit, and the only thing the tick changes is the text on screen and whether the claim button is offered.
- **The share panel opens itself while the room is waiting for its second player, and is only ever shown to a player.** §5.1 puts it in the flow between "create" and "the first other visitor arrives", which is the window in which the link is the thing the room needs, so that is when it is open without being asked for. It collapses once Black is in, because the board wants the space at 360 px — but it stays reachable from the bottom bar for the life of the room (see the second pass). A spectator never sees it: §6.4 says board and status, no controls. *(Superseded in part: the first version placed it above the board and removed it entirely at the join.)*
- **A room with one player in it says so in the status bar.** GDD §6.2 pairs an inert board with a status bar that says why, and "Your turn" over a board that refuses every tap is the one thing it must not say. `StatusBar` takes a `waiting` flag and this page passes `waiting={!bothSeated}`. *(Superseded: the first version left the headline reading "Your turn" and let the share panel carry the message, because `chromeModel` belongs to item 5 — the flag was added there once it was clear this was the only correct place for it. See the second pass.)*
- **Resign appears only once both seats are filled** — the same condition as Offer draw. `/action` refuses *every* action, resignation included, while a seat is empty, so a resign button before the opponent arrives could only ever be refused, and a button that silently does nothing is worse than no button. (`DECISIONS.md` records the opposite intent for the API — "resign stays available so an abandoned room can be closed" — but the route as written calls `requireBothSeats` before the action type is looked at. Reported, not changed; if the route is relaxed later this condition can be too, and nothing else needs to move.)
- **Resign, draw and rematch are one tap each, with no confirmation**, as in hot-seat. The offer states are in the button's own label — "Offer draw" becomes "Draw offered" and disables for the offerer, "Accept draw" for the other side — so the pending offer needs no second place on screen to live.
- **The banner leads with the reader's own result.** "You win." / "You lose." / "A draw.", with `statusHeadline`'s "White wins — mill-out" underneath, mirroring hot-seat's structure ("Player 1 wins." over the same line): the bold line is the half the shared chrome cannot know, and §6.3's result-and-reason is still on screen in one wording. A spectator gets the colour instead ("White wins.") and no buttons.
- **The two-context e2e derives whose ply it is from the script, and then makes the page confirm it.** `MILL_OUT_GAME` is a flat list of actions with no owner, and re-deriving the owner with the engine would be the "test the engine against itself" trap item 6 avoided. The turn passes on every action except the removal a mill earns (§4.5), which is enough to say who acts; before every single tap the spec waits for *that* page to say "Your turn". If the derivation is ever wrong the wait fails, so the bookkeeping is checked 32 times per run rather than trusted.
- **Two assertions carry a raised timeout, both for the same reason.** §7.3's slow interval is 5 s, which is longer than Playwright's default expectation timeout, so the two updates that cross on it need to be told to wait: the rematch offer (a finished game polls slowly) and the forfeit reaching the player who was on the clock (it is their turn, so they poll slowly right up to the moment they lose). Raising those two timeouts is the honest fix — the alternative was to poll faster than the GDD says in order to make a test go green. *(Superseded by the eleventh pass: there are many more than two now, and they have four distinct reasons, which that section lists. The principle — raise the timeout, never the poll rate — is the half that still holds.)*
- **The timeout spec creates its room through the API and seeds both seats.** The UI offers the four real choices of §5.3, the shortest of them a minute; `MORRIS_E2E=1` lets the API take a 12-second timer instead. The two tokens are written into the two contexts' `localStorage` in exactly the client's own format (`seatStorageKey`, `StoredSeat`), so the pages open already seated and the spec is about the clock and nothing else. Twelve seconds because the clock starts at the *join*: long enough to assert the claim is refused and not yet offered while it runs, short enough to wait out. The only waiting is on expectations — the claim button appearing, the clock's `data-urgent` — never on a fixed delay.
- **The refused claim is asserted against the API, not the UI.** The client does not show Claim win before the clock expires, so there would be nothing to click: the spec posts the claim with the opponent's real token and asserts the 409 and its reason, then plays the honoured claim through the button. Both halves of §5.3's "the server validates elapsed time" are covered, and the first half cannot pass by accident because the button was merely missing.

## Online mode, second pass (critic findings)

- **A resignation re-pins itself; every other action is still dropped on a 409.** Resign was sent through `/action` with the version the board was drawn from, so for up to 1.5 s after every opponent move — the poll gap — a resignation came back 409 and vanished with nothing on screen. That is not §6.2's "illegal tap silently ignored": a board tap in that window is protected because the board is inert until the poll lands, whereas a resignation is legal at the version the server actually holds, and the gap is exactly the moment a player decides to resign. `resignGame` now re-pins to the version the 409 names and re-sends, up to three attempts, which is what `mutateRoom` already does server-side for the endpoints that carry no version. Board actions keep the old behaviour on purpose: they are judged against the position they were drawn from, and re-sending one at a version the player never saw would be the client deciding what a move means.
- **A 403 that can only mean "not your seat" gives the seat up.** The client believed a stored token until something else contradicted it, so a token for a room whose seats are both really taken rendered an enabled board and controls whose every tap was refused, for ever — the "client trusts its own state" pattern §7.3 forbids. `run` gained a reading of the refusal, and when it says the seat is gone the seat is dropped here *and* in `localStorage`, so a reload does not restore it and the page becomes a read-only visitor (§6.4). *(Superseded in the tenth pass: this pass identified the refusal by the shape of the request that earned it — a `SeatRefusal` predicate per call site, enumerating the other 403s each could have provoked — which was one 403 short and, once the sentence itself was compared, was doing nothing but delaying eviction. There is one reading now, and it is `REFUSAL.notAPlayer`. See there.)*
- **The seat cannot be checked before the first refusal, and that is a contract limit, not a choice.** `PublicRoom` carries no tokens and `seats` is two booleans, so nothing a client may read says whether *its* token holds a seat; every token-bearing endpoint mutates. The only side-effect-free probe available is a deliberately stale `expectedVersion` on `/action` — 403 for a stranger, 409 for a seat holder — which works only because of the order of two guards inside `mutateRoom` and sends a resignation that must never be executed. Not worth it. A validation endpoint, or a seat echoed on the public view, would be a wire change and is not this item's to make.
- **A room with one player in it says so, in §6.2's own words.** Until the second seat is claimed there is no turn to report: the board is shut and every action is refused, and "Your turn" over a board that refuses every tap is the one thing the status bar must not say. `StatusBar` now takes `waiting` (added by item 5 at this item's request) and the page passes `waiting={!bothSeated}` while handing over the viewer's real colour throughout — so the headline reads "Waiting for an opponent…" for either seat, and still leads with the result once the game is over. The first attempt withheld the viewer's colour instead, which produced "White to play" — true, but a sentence a seated player should never read about themselves, and it was a workaround for a component this item may not edit rather than a design. The share panel below no longer repeats the sentence: it says what to do about it ("Send this link").
- **The share link lives in the bottom bar and outlives the join.** §6.1 lists it there with the counts and the other controls; it was above the board and only while the room had one player, so after the join there was no way to get the link from the UI at all — and a game in progress is worth sending to someone who will watch it (§6.4). It is now a **Share link** / **Hide link** control in the bottom bar, expanded by default while the room is waiting and collapsed once both seats are filled, so the board keeps the space at 360 px. A spectator still gets no controls at all.
- **The link input is a control, so it carries the 44 px floor.** It selects itself on focus and the copy-failure path tells the player to select it by hand, which makes it a tap target and not a caption; `py-2` gave 34 px. It uses the same `min-h-11` as every other control now.
- **The join pre-check states one server rule, not two.** `result !== null` could only fire on a room with an empty Black seat, which no endpoint can produce, so it was dead code that also stated a rule outside the engine and the server. Gone. The `seats.B` half stays: it is the same condition `/join` itself refuses on, checked only to skip a request that would certainly be refused, and the 409 remains the authority — the client believes nothing it has not been told.
- **`useRoom`'s two load-bearing rules are pure modules now.** `adoptRoom` (the version guard that stops a poll undoing a mutation) is `roomState.ts`, and the request gate is `SingleFlight` in `singleFlight.ts` — used twice, by the poll and by the mutation path, so the "one at a time" rule exists once. Both are covered by tests that fail if the rule is deleted, which was the point: a hook cannot be tested in this repo without a DOM harness the dependency budget (§8.6) does not allow, so the answer was to move the rules out of the hook rather than to import a testing library.
- **A 404 from a mutation still does not throw a live game away.** Only the polling `GET` sets `missing`; a mutation with nothing to adopt re-reads, and the read is what decides. Kept deliberately, now that a version conflict on a room the store cannot see answers 404.
- **Every refusal sentence in a test comes from the API's `REFUSAL` table**, not a literal, so a reworded refusal cannot leave a green spec asserting a sentence the server no longer sends. *(This was true of one spec when written and quietly false of two others by the eighth pass — see the ninth, which fixed the e2e and left three unit-test literals standing, and the tenth, which swept both trees.)*

## Online mode, third pass (critic findings)

- **A resignation re-pins its version, but never crosses a game boundary.** The retry added in the second pass re-sent on *any* 409, carrying only a new version — so a page frozen on game 1 could resign game 2, a game the player had never seen and in which their token played the other colour (§5.4). `resignGame` now takes the `PublicRoom` the resignation was decided in and re-sends only when the refusal is a genuine version conflict (the version moved: a state refusal such as "the game is over" leaves it alone, and re-sending one is a byte-identical repeat of a request already refused), **and** the room that came back is the same `gameNumber`, **and** that game is still live. Anything else is dropped like any other lost tap.
- **A refusal is judged against the room that carried it.** *(Moot since the tenth pass: nothing about the room is read any more, so there is no colour to derive and no stale one to derive it from. Kept because the bug it names is the reason to distrust this whole class of reasoning.)* The second pass compared the refusal's room to `you`, which is derived from the room the *client* is holding — so a client one rematch behind judged a fresh 403 with a stale colour, and `SEAT_IF_STILL_THEIR_CLOCK` inverted: `/claim-timeout` answering "the clock is yours" to a legitimate seat holder deleted their token, and §5.1 makes that seat unrecoverable. The colour now comes from `result.room.gameNumber`, inside `seatIsRefused`, so the reading and the room it is read against can never come from different games.
- **The seat-refusal rule is a tested module, not a constant in a component.** `src/lib/client/seatRefusal.ts` holds the whole decision; inverting it turns its tests red. *(It held three readings as well until the tenth pass deleted them.)* They decide whether a player keeps a seat they cannot get back, which is too much weight for code no test touches. `api.ts` has unit tests for the same reason — the retry bound, the non-conflict 409, and the game-boundary case are exactly where the last two bugs lived, and all three were unexercised.
- **A room that 404s mid-game shows the room-is-gone screen.** It was gated on `room === null`, true only before the first successful read — so the one case a live player needs it, a room expiring under them (§7.2 keeps them seven days), was the one case it could not appear: a frozen board, "Your turn", and a Resign button that 404s in silence. It is gated on `status === 'missing'` now, which is what a 404 on the read means.
- **Every request abandons itself after eight seconds.** A browser does not time `fetch` out, and both the poll and the mutations run through a `SingleFlight`, so one connection that is accepted and never answered left the gate held and stopped the client dead — no polling, and `visibilitychange` unable to restart it. `AbortSignal.timeout(REQUEST_TIMEOUT_MS)` on every request turns that into an ordinary failed result, which releases the gate; the next poll asks again. Eight seconds is more than five polls, so nothing legitimate is cut off, and a GET is idempotent anyway.
- **The room page reads the room once at load.** Seat resolution used to make its own `fetchRoom` while the hook's first poll was in flight — two independent reads of the same room in the same tick, on different gates, which only `adoptRoom`'s version guard made harmless. It now waits for the room the hook has already fetched (through a ref, so the effect does not re-run on every poll) and decides from that.

## Online mode, fourth pass (critic findings)

- **A 2xx is a success only if what came back is the reply that was asked for.** An unreadable body was being reported as `{ok: true, data: null}`, and every caller dereferences that immediately — `adoptRoom` reads `version` and `serverNow`, the seat resolver reads `token` — so one intermediary answering 200 with an HTML sign-in page killed a live game. The eight-second abort added in the third pass made it *more* reachable, not less: a response whose headers arrive inside the timeout and whose body does not produces exactly that shape. `send` now takes a predicate per endpoint and answers `ok: false` unless the body both parsed and looks like the thing that was requested.
- **What that predicate is, and is not.** It checks only the envelope this client dereferences — the `PublicRoom` fields `adoptRoom`, the clock and the chrome read, plus a 24-cell `board` (`POINT_COUNT`, imported, not restated) and a `turn` — and, for `/join` and `/api/game`, that a token is a non-empty string before it is written to `localStorage` unread. It is **not** Zod, not a second copy of the wire contract, and it never asks whether a position is legal: that is the engine's and the store's, and the store already validates on the way out of Redis. Its job is to tell "our server answered" from "something else answered 200" — the same reasoning as the store's inbound gate, at the other end of the wire.
- **`send` cannot throw, including while building the request.** `AbortSignal.timeout` is missing on iOS Safari before 16, and it was being evaluated outside the `try`, so on those browsers every request would have thrown synchronously — and since both callers run `send` through a `SingleFlight` with `void`, that is an unhandled rejection and a page stuck on "Loading…" with nothing left to retry it. The timeout is now an `AbortController` and a timer, built inside one guarded region that turns anything at all into a failed result. The timer covers the body as well as the headers, which is the hang it was added for, and is cleared in a `finally`.
- **"Spectating" waits for the seat to be resolved.** The bottom-bar label was derived from `you === null`, which is also true in the second between the first read and the answer from `/join` — so a player who was about to be seated was shown the §6.4 word for someone who never will be. It now shows "Finding your seat…" until `seated`, the same flag the status bar already used. That also repairs the read-only spec: "Spectating" is now proof that resolution finished, which is what makes the "no controls" assertions after it assertions about a real visitor. *(Corrected in the tenth pass: there were six, and two of them — `rematch` and `claim` — named controls no viewer of that room has, seated or not. The live, timer-less list is four now, and the other two are asserted in rooms that can actually draw them.)* *(Count corrected again in the twelfth pass: it is three — `resign`, `draw`, `share-toggle` — because the eleventh pass moved `share` out to the storage-blocked visitor's room, the only one that can draw it. Both places that said "four" now say where the number lives instead of restating it.)*

## Online mode, fifth pass (critic findings)

- **One rule, on both sides of the door: a reply is acted on only when it is this server's.** The fourth pass checked the body of a 2xx and left the refusal path a raw cast, which was worse than the bug it replaced — the room on a 409 or a 403 is dereferenced by `adopt`, by the resign retry and by the seat check, so a refusal carrying `{version: 999}` crashed the page and unmounted it, with no recovery but a reload. A refusal is now believed only when it arrives in the API's own `ApiError` envelope, and its room only when it passes the same check the success path uses; a room that fails is dropped, which leaves the caller to re-read.
- **A status is part of the envelope, not something separate.** `useRoom` reads 404 as "the room is gone", which is terminal — polling stops and nothing restarts it — and an edge 404, a proxy error page or a mid-redeploy has exactly that status with none of this server's body. Anything unattributable is now reported as status 0, the same as a dead network: nothing was heard from the server, so there is no status for any caller to act on. The one thing that ends a live game is this server saying, in its own words, that the room is gone.
- **The shape check is derived from the declared types, not written out by hand.** `PUBLIC_ROOM_FIELDS` and `GAME_FIELDS` are `{ [K in keyof T]-?: Check<T[K]> }`, so adding a field to `PublicRoom` or `GameState` stops this file compiling, and a checker for the wrong type does not line up — both verified by making them fail. That is what the hand-written version cost: it omitted `game.result`, the one field whose absence is fatal (the banner and `statusHeadline` destructure it), on the first attempt. The closed alphabets come from the engine's own `PLAYERS`, `PHASES` and `REASONS` lists rather than being restated. It is still a shape check and never a legality check: whether a position is reachable belongs to the engine and the store.
- **A draw tap re-reads the room before it is sent.** `/draw` is offer and accept in one call (§4.6), so which one a tap *is* depends on the room when it lands, while the button's label was drawn from a room up to a poll old — or arbitrarily old in a background tab, which does not poll at all (§7.3). Two things flip an offer into an acceptance unseen: the opponent offering, and a rematch replacing the game (§5.4). `offerDraw` read the room immediately before the write and sent only if what the player was shown still described what would happen. *(Superseded twice, and now gone: the game-boundary half moved to the server in the sixth pass with `gameNumber`, and the offer half in the eighth with `accepting`. There is no read before the write any more — see below.)*
- **The request timer covering the body is pinned.** Moving `clearTimeout` to just after `fetch` resolves — leaving the headers covered and the body not — used to break nothing. A fake-timer test now fails if it moves.

## Online mode, sixth pass (the `/draw` contract change)

- **Which game a draw tap was about now travels with the tap.** `/draw` takes an optional `gameNumber` and refuses a mismatch with a 409 before it judges anything else, so the boundary is settled by the one party that can settle it atomically — a client-side comparison can always be overtaken between its read and its write. `offerDraw` sends `from.gameNumber`: the game the *button was rendered from*, never the one just read. That is the whole point of the field. A value taken from a fresh read would always match and would say nothing.
- **The pre-write read stayed for one round, for one reason, and then that reason was taken away too.** It was the only thing that could see "same game, one poll behind, the opponent has offered in the meantime" — both taps carry an identical `gameNumber`, so nothing in the request distinguished "I am offering" from "I am accepting something I was never shown". But a read before a write narrows a window and never closes it: an offer can land *inside* the request. `accepting` (eighth pass) settles it where it is written, so the read is gone and with it the extra GET per draw tap.
- **Two mechanisms, two specs — and the first version of that claim was only half true.** "a draw tap cannot plant an offer in the game that replaced it" pins the boundary: the flags are identical in both games, so only `gameNumber` can tell them apart, and removing it from the body reddens that spec alone. The offer comparison was *asserted* to be pinned by "a draw offer cannot become an acceptance the player never saw" — but that spec crosses a rematch, so the server's `gameNumber` refusal produces the same outcome, and deleting `sameOffersAsShown` outright left every draw e2e green. The scenario that isolates it is the one this file calls the likelier case and had no spec for at all: **same game, hidden tab, opponent offers, tap.** That is now "a draw offer that arrives during the same game is not accepted unseen", and deleting the comparison reddens it and nothing else. Each guard is now pinned by a spec the other guard cannot satisfy.
- **The harm the boundary check prevents is not only an accepted draw.** An offer left standing in a game the player never saw is what turns their opponent's next "Offer draw" tap into an acceptance — so the spec asserts both flags are still false in the new game, not merely that it has no result.
- **`gameNumber` is not sent to `/rematch` or `/claim-timeout`**, agreeing with the API's reasoning: a stale rematch can only land on a finished game, and its worst outcome is a rematch the player asked for slightly early; a stale claim succeeds only if the clock really has run out on the game the server is holding, which is an entitlement the claimant has either way. A draw is the only one of the three that ends a live game against a player who never saw the position.

## Online mode, seventh pass (critic findings)

- **A reply has to be about the room that was asked for.** The shape check covered every declared field but read `id` as "a string", though every caller has the id in hand. A well-formed `PublicRoom` belonging to *another* room is the worst kind of wrong answer: it draws a stranger's board and reports a stranger's turn, and because a version only climbs, a higher one from elsewhere makes `adoptRoom` reject every genuine poll that follows — the tab is dead until a reload, and the player cannot raise the version by moving, because it is not their turn on the board they are being shown. `send` now takes the room a request is about, and `isRoomFor(id)` is what both the success body and the room on a refusal are checked with. `POST /api/game` has no id to compare against yet, so its reply is checked for agreeing with itself: the room it hands back is the room it names.
- **The spec for that had to be built to fail.** The first version used a second room straight after creation, whose version was *lower* than the room under test — so `adoptRoom`'s monotonic guard dropped it and the spec passed with the check deleted. It now plays the other room on until it genuinely out-versions ours, and asserts that precondition before relying on it. Without that, the test would have been describing a fix it never exercised, which is the same mistake as the draw spec above, twice in one item: **a spec that cannot fail is worse than no spec, because it is also a claim.**

## Online mode, eighth pass (the `accepting` contract change)

- **What the button said it would do travels with the tap.** `/draw` takes an optional `accepting: boolean` and compares it against the *opponent's* flag inside `mutateRoom`, so the question "was this an offer or an answer to one?" is settled under the same optimistic-concurrency guard as the move itself. `offerDraw` sends the bit the label was chosen from — literally `drawOfferedToYou`, the same expression the button's text reads — so what the server is told the tap meant is what the player read.
- **One bit, not the `drawOffer` pair.** The API's reasoning, adopted here: the caller's own flag is not part of the decision, because offering twice is already a no-op, so echoing the pair would refuse taps that are perfectly good. `accepting` refuses exactly the taps whose meaning would otherwise change, in both directions — an offer that would land as an acceptance because theirs arrived inside the request, and an acceptance that would land as a fresh offer because theirs had lapsed.
- **The pre-write GET is deleted, not re-justified.** It narrowed the window to a round trip and could never close it; the room is judged where it is written now. That also removes a request from every draw tap, and removes the last place this client checked something the server was better placed to check.
- **The 404 that ends a game is compared against the sentence, not just the shape.** `REFUSAL` moved to `@/lib/api/refusals`, a file with no imports at all, so the client can hold it: `useRoom` now stops polling only on `404` **and** `REFUSAL.roomNotFound`. A stray `{"error": "Not Found"}` from an edge or a proxy no longer ends a live game — and the old spec passed only because it had chosen `{"message": …}`, a body the old check would have rejected anyway. The spec now sends the shape that actually defeated it. Verified in the built bundle: the client chunks carry the refusal sentence and nothing from the store.

## Online mode, ninth pass (critic findings)

- **A post-click assertion has to wait for the click to be answered.** The refusal half of the room-identity spec asserted "still your turn" and "still eight in hand" straight after `playActions`, which returns as soon as the click is dispatched — so both were already true at that instant and `toHaveText` passed on its first poll, before the fulfilled 409 was ever processed. Replacing the id check on the refusal path with the bare shape check left the whole suite green. It now waits for the POST's response *and* for the read the client makes when a refusal carries nothing it can use, and then asserts things the stranger's room would actually break: one White piece on the board rather than three, eight in hand rather than six, and point 0 — where the tap was aimed, so nothing else could put a piece there — still empty. Verified by making it fail: `Expected: "1" / Received: "3"`.
- **That is the same mistake as the version-guard one, in the same test.** The first half of this spec had already been rebuilt once because a lower-versioned stranger's room could never have been adopted; the second half was dead for a different reason and survived. Two dead halves in one spec is a pattern, not an accident: **a "still true" assertion after an action is worthless unless something is waited for and the assertion could have gone the other way.** Every other post-click assertion in both spec files was checked against the bug it names.
- **The refusal sentence is imported in all three places now.** `useRoom` compared against `REFUSAL.roomNotFound` while two tests spelled it out, which put a constant this codebase's newest guard turns on into three homes — and against a written decision saying otherwise. The e2e imports `REFUSAL` from `@/lib/api` (as the timeout spec already did) and the unit test from `@/lib/api/refusals`. It failed safe — a rewording would have reddened the mirrors loudly — but the decision said one home, so it has one.

## Online mode, tenth pass (critic findings)

- **§6.4's "no controls at all" is asserted where a control could actually appear.** The read-only spec listed six test ids after "Spectating" and two of them — `rematch` and `claim` — could not fail: that room is live and has no timer, so `GameOverBanner` returns `null` for every viewer and `claimable` is false for every viewer. - **A vacuous assertion was removed rather than left as decoration.** The evicted-seat spec listed `claim` in the same way, in a room with no timer. A list of ids that reads as coverage and cannot fail is the same defect as the one the seventh pass named: a spec that cannot fail is also a claim.
- **A 403 is read as seat loss from the sentence, and there is no second reading.** `seatIsRefused` used to identify the refusal by the shape of the request that earned it: three `SeatRefusal` predicates, one per call site, each enumerating the other 403s that call could have provoked. The enumeration named two; there are three. `/action` refuses `{type: 'forfeit'}` with `REFUSAL.forfeitIsServerIssued` **before** the turn check, so `SEAT_IF_STILL_OUR_TURN` — "unless the turn has moved on" — could not rule it out, and a forfeit sent on our own turn would have read as "this token is not a seat" and deleted a real player's token (§5.1: unrecoverable). It was unreachable only because `interpretTap` never produces a forfeit, which is a property of the caller, not of this module. So the decision is now the sentence: a seat is given up for `REFUSAL.notAPlayer` and for nothing else. That is complete by construction rather than by enumeration — `mutateRoom` answers it when `seatOf` finds no seat, ahead of the version, the turn, the clock and the action, about the very room it hands back, and no state exists in which a token that genuinely holds a seat earns it (a rematch swaps which colour each token holds, §5.4; it never unseats either). A 403 the API grows next cannot evict anyone, and neither can an action this module did not anticipate.
- **The predicates were then deleted, because a disambiguator for a gate that no longer exists is not a safeguard.** They existed to tell one 403 from the others when the client could not read which was which; once the sentence is compared, the only thing they could still do was answer `false` to a `notAPlayer` refusal whose room says the turn has moved on — keeping a seat the server had just said definitively does not exist. That is not caution, it is the client outranking the server, which is the one thing CLAUDE.md and §7.3 forbid: the client adopts what the server returns and never trusts its own optimistic state. It was reachable through an ordinary 1.5 s poll gap, not a contrivance, and what it bought was a page still captioned "You play White" over an enabled board until some later tap happened to land on a matching turn. Verified before deleting rather than argued: an impostor page, reads frozen, a real move landing in the gap, then a tap — the server answered `notAPlayer` and the page kept the seat and the token. `run` takes one argument again, the five call sites are identical, and `SeatRefusal`, `SEAT_ONLY`, `SEAT_IF_STILL_OUR_TURN`, `SEAT_IF_STILL_THEIR_CLOCK` and the colour derivation inside `seatIsRefused` are all gone.
- **The collapse is a behaviour change, so it has a spec of its own.** "a seat the server does not recognise is given up even after the turn has moved on" is the probe above, made deterministic: the impostor's reads are cut off, White plays inside the gap, and the tap that follows must leave the page `Spectating` with the token gone from `localStorage`. The pre-existing eviction spec cannot catch this — its tap lands on its own turn, so both behaviours evict — which is exactly why the change could not ship on the older spec alone. Reinstating the predicate reddens the new spec (`Expected: "Spectating" / Received: "You play White"`) and leaves the old one green.
- **One e2e changed what it pins, for the better.** "a claim refused because the clock is now ours does not cost the seat" used to be the only thing standing behind `SEAT_IF_STILL_THEIR_CLOCK`, and after the sentence gate landed it stopped discriminating anything — it passed whether or not that predicate was inverted. It now pins the sentence gate itself: `/claim-timeout` answers `yourOwnClock`, which is not `notAPlayer`, so deleting the sentence comparison evicts a legitimate seat holder and reddens it. Its name still says what it proves; only the mechanism underneath it changed.
- **The `REFUSAL` decision is now true of the whole item.** Three sentences were still hand-spelled in unit tests — `gameOver` and `differentOffer` in `api.test.ts`, `notAPlayer` in `seatRefusal.test.ts` — plus a fourth, `'not a player'`, that was a *paraphrase* of a refusal the server never sends and so would have survived any rewording silently. All four import the constant now. Both trees were swept by matching every value in the table against every test and spec file; what is left is prose in test names, the engine's own `IllegalActionError` messages (which are not this API's to word), and `endpoints.test.ts`'s table-pinning test, which spells the sentences out on purpose so a rewording has one place to be noticed.

## Deferred (recorded, not fixed)

The build rules changed part-way through: one critic round per item, no mutation
testing, no tests of tests, no test file over 300 lines, and no test without a
production behaviour it exercises. `src/lib/api`'s suite was rewritten to fit —
one 4,605-line file of 389 tests became ten files of 123, holding GDD §8.2 as the
floor. Production coverage did not move: every file in `src/lib/api` and
`src/app/api` is still at 100% statements, branches and functions, which is the
evidence that nothing cut was the last thing holding a branch.

What that cost, recorded here so the next reader does not mistake it for an
oversight. Listed worst first; none is a defect today.

- **Nothing checks that `src/lib/api/refusals.ts` stays import-free.** That file
  exists so a `'use client'` module can compare a 404 against
  `REFUSAL.roomNotFound` without dragging the store — and therefore the Upstash
  client — into the browser bundle. The test that enforced it parsed the file
  with the TypeScript compiler API, which is a test of a test under the new
  rules. What survives checks the module's *surface* (`exports exactly
  ['REFUSAL']`), so a stray re-export is still caught; a plain `import` used
  internally is not. The file's own header says it imports nothing; that comment
  is now the whole guard.
- **No unit test carries a game to a rules-driven ending through the API.** Every
  API test ends its game by resign, forfeit or agreed draw. Hand exhaustion →
  movement → mill-out, blocked and the 50-move draw reach the engine's suite and
  the e2e, not the routes. The `gameOver` guards are reason-independent so no
  branch is lost, but "the API can carry a real game to a natural finish" now
  rests entirely on `npm run test:e2e` (GDD §8.3 does put it there).
- **Guard ordering is sampled, not swept.** Three orderings are pinned where they
  decide an answer — token→version→turn→legality in `quality-bar.test.ts`,
  state→timer→seat in `claim-timeout.test.ts`, seats→gameNumber→state in
  `draw.test.ts`. The rest were a generated matrix and are gone. Ordering is the
  thing most likely to regress silently under a refactor of `write()`.
- **Per-route id exactness** is probed on `GET` and `/draw` only; **`clockRunning`**
  is checked in five situations rather than ten; **the claim-vs-move race** runs
  eight rounds rather than forty and no longer asserts that both refusal kinds
  occur; the hostile-body table is six rows rather than nine. These weaken
  statistical arguments, not propositions.
- **A duplicated `requireBothSeats(room);`** in a mutating route is invisible
  again. The test that caught it grepped route source text.

One live contract worth stating, because it is easy to break from the other side:
the client sends `accepting` and `gameNumber` on every `/draw` call. Two
simultaneous *plain* offers do agree a draw — correctly, since both players asked
— but the `accepting` flag is what stops an offer that crossed in flight from
being read as an acceptance. If the UI ever stops sending it, that race reopens.

`Board.tsx`'s dimmed-piece opacity went 0.35 → 0.45. At 0.35 the composite
against the `#e8dcc8` plate is about 2.4:1, under WCAG 1.4.11's 3:1 floor for a
graphical object that carries meaning. Neither §6.2 nor §6.5 cites that floor —
§6.2 only asks for "dimmed" — so this is a nudge taken, not a defect fixed.

## Deploy readiness (gauntlet item 9)

- **`vercel build` was skipped, not run, and not failed.** GDD §8.5 asks for it
  "if the CLI is present and linked". It is present nowhere: `which vercel` finds
  nothing, `node_modules/.bin/vercel` does not exist, and there is no `.vercel`
  directory, so the project is not linked to a Vercel project either. Installing
  the CLI and running `vercel login` / `vercel link` needs an interactive
  browser login, which this build was told not to attempt. `npm run build` is
  the gate that did run, and it is the one `vercel build` would have wrapped.
- **No `vercel.json`.** Nothing about this project needs one: the framework is
  detected, every API route is `force-dynamic` by declaration rather than by
  config, and there are no rewrites, headers or crons. A file that only restates
  defaults is a file that goes stale.
- **The environment section of `README.md` is written against the code as it
  stands and was re-checked at the end**, because it drifted repeatedly while the
  store's environment handling was still moving. Specifically true as committed:
  blank and whitespace-only values count as unset everywhere; whitespace is
  trimmed everywhere except the timer half of `MORRIS_E2E`, which compares the
  raw value so a trailing space in a `.env` leaves the escape shut; credentials
  are read as pairs with `KV_` first and never cross-married; and "a deployed
  runtime" means `VERCEL=1` with a `VERCEL_ENV` that is not `development`, with
  absent, blank and unrecognised values all counting as a deploy so the guard
  fails closed.
